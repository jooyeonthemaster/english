## 0. 목표

전 학년 영어 기출 지문 **4,537건**에서 학습 가치가 있는 모든 어휘를

## 2. 출력 — 지문 1건당 JSON 파일 1개

경로: `experiments/vocab-corpus-20260728/raw/<passageId>.json`
**파일 전체를 항상 새로 쓴다(전면 교체).** 부분 수정 금지 — 중간에 죽어도 재실행이 무해해야 한다.

```jsonc
{
  "passageId": "ebsi_go3_20260324-q31",
  "specVersion": "v3",
  "sentences": [
    { "i": 0, "en": "원문 문장 그대로", "ko": "자연스러운 한국어 해석" }
  ],
  "entries": [
    {
      "surface":   "quantified",          // 지문에 나타난 표층형 그대로(굴절 포함)
      "lemma":     "quantify",            // 표제어(사전 표제형)
      "pos":       "verb",                // 아래 §3 고정 목록
      "senseKo":   "수치로 환산하다",       // 이 문맥에서의 뜻 — §5 규범 준수
      "senseEn":   "to express or measure something as a quantity or number",
      "sentenceIndex": 3,                 // sentences[] 인덱스
      "example":   "Art of any form, by its very nature, cannot or should not be quantified",
      "exampleKo": null,                  // §6.1 — 40단어 초과 문장을 잘랐을 때만 채운다
      "inflection": "past_participle",    // §3.5.6 고정 목록. 없으면 "base"
      "tier":      "core",                // §4
      "difficulty": 3,                    // 1~5 초안(후속 정량화로 보정됨)
      "trap":      { "kind": "polysemy", "note": "…" },   // 없으면 null
      "collocation": "be quantified",     // 없으면 null
      "confusable":  ["quantity", "qualify"]              // 없으면 []
    }
  ]
}
```

### 필수 불변식 (위반 = critical)
1. `sentences[].en` 을 이어붙인 비공백 문자열은 원문 `text` 의 비공백 문자열과 **정확히 같아야 한다.**
2. `example` 은 `sentences[sentenceIndex].en` 의 **연속 부분문자열**이어야 한다. 창작·재구성 금지.
3. `surface` 는 `sentences[sentenceIndex].en` 안에 **실제로 존재**해야 한다(대소문자 무시).
4. 모든 필드는 위 스키마의 키 이름을 **글자 그대로** 쓴다. 임의 작명 금지.
   (2026-07-27 실장애: 모델이 `rawText` 를 `ocrText` 로 자유작명해 전건 실패)
5. `entries` 는 빈 배열일 수 없다.

## 3. `pos` 고정 목록

`noun` · `verb` · `adjective` · `adverb` · `preposition` · `conjunction` ·
`phrasal_verb` · `idiom` · `collocation`

숙어·구동사는 통째로 한 항목이다(`surface` 에 구 전체, `lemma` 에 사전형).
감탄사(Hurray, Alas)는 학습 가치가 낮아 **추출하지 않는다**(목록에 없는 품사는 곧 제외 대상이다).

### `collocation` pos 는 명사복합 전용이다

파일럿에서 이 pos 가 기준 없는 쓰레기통이 됐다 — 명사복합(`car trouble`)·형용사+전치사(`sure of`)·
형용사구(`well known`)·동사+전치사(`see as`)가 한 통에 섞였고, **같은 현상을 항목으로 뽑을지
필드로 남길지가 지문마다 갈렸다**(견본은 `visual arts` 를 필드에만 남겼는데 다른 지문은
`building material` 을 독립 항목으로 만들었다).

| 형태 | 처리 |
|---|---|
| **명사 + 명사** — `building material`, `job roles`, `dating rule` | **`pos: collocation` 독립 항목** ✅ |
| **형용사 + 명사** — `visual arts`, `internal conflict`, `competitive ecosystem` | ❌ 구 전체를 한 항목으로 만들지 마라. **형용사 항목과 명사 항목을 둘 다 만든다**(→ §3.1 의무). 구는 양쪽의 `collocation` 필드에 적는다 |
| 동사 + 전치사 — `see as`, `compete for` | `pos: phrasal_verb` (§3.5.3) |
| 형용사 + 전치사 — `sure of`, `responsible for` | **그 형용사 항목** + `collocation` 필드에 `be sure of` |
| 그 밖의 연어 | `collocation` **필드**로만. 독립 항목을 만들지 않는다 |

**명사+명사만 독립 항목**이라는 선을 그은 이유: v3 파일럿에서도 `internal peace` / `outside threats` /
`predatory rivals` / `early stages` 를 어디로 보낼지 지문마다 갈렸다. "하나의 개념인가"를 판단시키면
영원히 수렴하지 않는다. 통사 형태로 기계적으로 가른다.

### 3.1 형용사+명사 짝 의무 — `collocation` 을 적었으면 짝도 항목이어야 한다 (2026-07-29 신설)

> **형용사 항목의 `collocation` 에 `<형용사> <명사>` 구를 적었다면,
> 그 명사도 반드시 같은 파일에 독립 항목으로 존재해야 한다. 역도 성립한다** —
> 명사 항목의 `collocation` 에 같은 구를 적었다면 그 형용사도 항목이어야 한다.

`collocation` **필드는 항목을 만들었다는 영수증이지, 항목을 대신하는 물건이 아니다.**
필드에 `glittering gems` 를 적고 `gems` 항목을 만들지 않으면 그 명사는 DB 에서 사라진다 —
형용사 카드의 부속 문자열로만 남아 3단계 집계에도, 4단계 병합에도, 학생 단어장에도 오르지 못한다.

**왜 이 절을 신설했나 (2026-07-29 감사)**: 이 의무는 원래 §3 표의 **금지문 셀 안에** 있었다
(`❌ 독립 항목 금지. 형용사·명사를 각각 항목으로 뽑고…`). 모델은 셀 첫머리의 **금지만 읽고**
뒤에 붙은 의무를 실행하지 않았다. 실측 **615/1,583 = 38.9% 위반, 724파일 중 352파일(48.6%) 영향** —
파이프라인의 기본 동작이었다. 검사하는 게이트도 없었다.

> **교훈: 의무는 금지문에 곁들이지 마라. 금지와 의무는 서로 다른 문장으로, 서로 다른 줄에 쓴다.**

이 조항은 **전면 기계 검사 대상이다**(§9 게이트 ⑨). 결함 4종 중 유일하게 100% 기계 판정이 가능하다 —
`pos: adjective` 항목의 2어절 `collocation` 을 뜯어 뒷단어가 같은 파일의 `lemma`·`surface` 에
있는지 대조하면 끝난다. 판단이 필요 없는 것은 사람에게 맡기지 않는다.

## 3.5 표제어(`lemma`)·어형(`inflection`) 규범 — 병합이 여기서 갈린다

파일럿에서 같은 어휘가 에이전트마다 다른 표제어로 적혀 병합이 시작조차 못 하는 사례가 나왔다
(`desired` vs `desire`, `be seen as` vs `see as`, `be responsible for` vs `responsible`).
아래를 **기계적으로** 따른다. 판단하지 마라.

### 3.5.1 분사형
| 지문에서의 기능 | `pos` | `lemma` | `inflection` |
|---|---|---|---|
| 동사로 작동 (시제·태를 이룸) | `verb` | **원형** (`reduce`) | `past_participle` 등 |
| 형용사로 작동 (명사 수식·보어) | `adjective` | **분사형 그대로** (`reduced`, `prevailing`, `developing`) | `base` |

판별: 그 자리에 `very` 를 넣거나 비교급을 만들 수 있으면 형용사다.

### 3.5.2 수동태 표층형 — `lemma`·`senseKo`·`senseEn` **셋 다** 능동형

적용 대상은 **be + 과거분사(동사)** 뿐이다. `be sure of`·`be responsible for`·`be well known`
같은 **형용사·명사 보어 구문은 대상이 아니다** — 그건 형용사 항목 + `collocation` 필드로 처리한다.
(이 구분이 없어 정규화 코드가 `be sure of` → `sure of` 라는 없는 표제어를 만든 사고가 있었다.)

| 필드 | 규칙 | ❌ | ✅ |
|---|---|---|---|
| `lemma` | 능동 사전형 | `be seen as` | `see as` |
| `senseKo` | 능동형 | `여겨지다` | `여기다` |
| `senseEn` | 능동 기술 | `to be drawn toward…` | `to make someone feel drawn toward…` |

`senseEn` 까지 규정하는 이유: `senseKo` 는 후속 병합이 정준화해 주지만, **`senseEn` 이 오염되면
정준화의 근거 자체가 사라진다.** 파일럿에서 `attracted` 가 lemma 는 능동인데 senseEn 이 수동으로
기술돼 적발됐다.

수동 함의는 전부 `collocation` 이 담당한다(`be seen as`, `be attracted to`).
표층형은 `surface` 가 이미 보존한다.

추가 위반 예시: `lost`→`잃다`(❌상실되다) · `associated with`→`관련짓다`(❌연관되다)

### 3.5.3 동사 + 전치사/부사

**먼저 이것이 구동사인지부터 판정한다.** 분리 가능 여부는 따지지 마라(전치사구동사와 구동사를
구분시키면 에이전트마다 갈려 표제어가 두 갈래로 쪼개진다) — 그러나 **아무 전치사나 붙이면 안 된다.**

> **예측 가능성 시험** — 이걸 통과해야만 `phrasal_verb` 다.
> 동사+조사 전체의 뜻이 **동사 단독의 뜻에서 예측되지 않는가?**

| 예 | 판정 | `lemma` |
|---|---|---|
| `give up` (포기하다) — give(주다) 에서 예측 불가 | ✅ 구동사 | `give up` |
| `bring about` (야기하다) — bring(가져오다) 에서 예측 불가 | ✅ 구동사 | `bring about` |
| `engage in` · `compete for` — 관용적으로 굳은 결합 | ✅ 구동사 | `engage in` / `compete for` |
| `arise in the forest` — arise(생기다) 그대로, `in` 은 장소 표시일 뿐 | ❌ 아님 | `arise` |
| `advise on safety` — advise(조언하다) 그대로 | ❌ 아님 | `advise` |
| `faced with a problem` — face(직면하다) 그대로 | ❌ 아님 | `face` |

전치사가 뜻을 바꾸지 않으면 **전치사를 떼고 동사만** 표제어로 쓰고, 구 전체는 `collocation` 필드에 적는다.

> **왜 이 시험을 추가했나(2026-07-28)**: 이전 문구가 "동사+전치사는 **전부** phrasal_verb" 였고,
> 이걸 문자 그대로 따른 추출기가 `arise on` · `arise in` · `face with` · `advise on` · `distinguish from`
> 을 만들어냈다. **표제어가 이렇게 쪼개지면 4,537지문 병합에서 `arise` 와 `arise in` 이 다른 단어가 된다.**
> 규범 자체의 결함이었으므로 규범을 고친다.

구동사로 판정되면 `lemma` 는 `compete for`, `engage in`, `bring about` 처럼 **동사원형 + 불변 조사**.

### 3.5.4 품사 전성 (동사↔동명사↔명사)
**서로 다른 `pos` 면 별개 항목이다.** `show`(verb) 와 `showing`(noun, 동명사 명사화)은 둘 다 수록 가능하다.

**판별 기준**(§3.5.1 의 `very` 삽입 테스트에 대응):
| 조건 | `pos` | `lemma` | `inflection` |
|---|---|---|---|
| 한정사·형용사의 수식을 받는다 (`the telling`, `careful planning`) | `noun` | `-ing` 형 그대로 | `base` |
| 목적어를 직접 취한다 (`defining roles`) | `verb` | 원형 | `gerund` |

### 3.5.5 파생어
접두·접미사가 붙어 **품사나 극성이 바뀐 단어는 독립 표제어**다.
`unavailability` 를 `available` 로 되돌리지 마라. `uniqueness` 도 `unique` 가 아니다.
어근과의 관계는 `confusable` 에 적는다.

### 3.5.6 `inflection` 고정 목록
`base` · `plural` · `possessive` · `comparative` · `superlative` ·
`past` · `past_participle` · `present_participle` · `gerund` · `third_person_singular`

동사 뒤 `-ing` 가 명사 기능이면 `gerund`, 형용사·진행 기능이면 `present_participle`.
목록 밖의 값을 쓰지 마라.

### 3.5.7 구(phrase) 표제어 정준화
파일럿에서 같은 현상을 4가지로 적어 표제어가 갈렸다(`out of their reach` / `by one's very nature` /
`tell oneself` / `a two-edged sword`). **sense 병합 이전에 표제어 병합이 시작되지 않는다.**

`lemma` 를 만들 때 기계적으로:
1. **선행 관사·지시사 제거** — `a two-edged sword` → `two-edged sword`
2. **소유격은 `one's` 로 치환** — `out of their reach` → `out of one's reach`
3. **재귀대명사는 `oneself` 로 치환** — `telling yourself` → `tell oneself`

지문형은 `surface` 가 이미 보존하므로 정보 손실이 없다.

#### 3.5.7.1 상관구문의 빈칸은 **대문자 A·B·C** 로 (2026-07-28 추가)

실측에서 상관구문 표제어 13개가 **소문자 `a`·`b`** 를 슬롯으로 썼다:
`not only a but also b` · `from a to b` · `neither a nor b` · `both a and b` · `either a or b` ·
`the more a, the more b` · `a is to b what c is to d` · `less a than b` · `as much a as b` 등.

**소문자 `a` 는 관사와 구별되지 않는다** — `as a result`(관사)와 `not a but b`(슬롯)가
같은 형태로 보이고, 학생 단어장에 그대로 노출되면 오독을 부른다.

> 상관구문·비교구문의 빈칸은 **대문자 `A` `B` `C`** 로 쓴다.
> `not only A but also B` · `from A to B` · `neither A nor B` · `the more A, the more B`

`one's`(소유격)·`oneself`(재귀)와 같은 계열의 규칙이다. 슬롯 표기를 통일하지 않으면
같은 구문이 표제어 여러 갈래로 쪼개져 병합이 시작조차 못 한다.

### 3.5.8 철자 변이
**미국식 우선, 하이픈은 붙여 쓰기로 통일**한다 — `savanna`(not savannah) · `phony`(not phoney) ·
`startup`(not start-up).

> **예외: 사전 표제형이 하이픈을 유지하는 어휘는 그대로 둔다** — `long-term`, `two-edged`,
> `self-deprecating`, `tried-and-tested`. 붙여 쓰면 `longterm` 처럼 **없는 단어**가 표제어가 된다.
> 이 조항은 `startup`/`start-up` 처럼 **두 철자가 실제로 병용되는 경우**에만 적용한다.

4,537건 규모에서는 에이전트 규율보다 코드 매핑이 안전하므로 3단계 정규화가 변이 매핑 테이블로
최종 수렴시킨다. 다른 철자는 `confusable` 에 남겨라.

#### 3.5.8.1 다어절 복합어의 하이픈 변이 (2026-07-29 실측 추가)

위 규칙이 **한 단어짜리 변이**(`startup`/`start-up`)만 다뤄서, **다어절 복합어**가 갈라졌다.
`<A>-<B> <C>` 와 `<A> <B> <C>` 는 같은 표제어인데 서로 다른 표제어로 적혔다
(`cell-phone company` ↔ `cell phone company`).

실측 724파일에서 **12군집**이 갈렸다. **매핑 방향을 여기에 못박는다** —
사전 표제형이 하이픈이면 하이픈이 정답이고, 그 반대면 띄어쓰기가 정답이다:

| 정답 표제형 | 흡수되는 변이 | 실측 |
|---|---|---|
| **`well-being`** (사전 표제형) | `wellbeing` | 9 : 1 |
| **`decision-making`** (사전 표제형) | `decision making` | 2 : 1 |
| **`problem-solving`** (사전 표제형) | `problem solving` | 3 : 1 |
| **`passer-by`** (사전 표제형) | `passerby` | 1 : 1 |
| **`trade-off`** (사전 표제형) | `trade off` | 1 : 1 |
| **`human-like`** | `humanlike` | 1 : 1 |
| **`round-trip`** | `round trip` | 1 : 1 |
| **`car-sharing`** | `car sharing` | 1 : 1 |
| **`ice-cream shop`** | `ice cream shop` | 1 : 1 |
| **`below-zero`** (한정 용법) | `below zero` | 1 : 1 |
| **`step-by-step`** (한정 용법) | `step by step` | 1 : 1 |
| **`go-to`** (한정 용법 형용사) | `go to` | 1 : 2 |

⚠️ **아래 셋은 품사가 갈리므로 기계 매핑에서 제외한다** — 하이픈 유무가 변이가 아니라 **품사 표지**다:
- `below zero`(부사구, *fell below zero*) ↔ `below-zero`(한정 형용사, *below-zero temperatures*)
- `step by step`(부사구, *proceed step by step*) ↔ `step-by-step`(한정 형용사, *a step-by-step guide*)
- `go to`(동사+전치사, §3.5.3) ↔ `go-to`(한정 형용사, *my go-to tool*)

이 셋은 **서로 다른 항목이 맞다.** 지문에서의 기능으로 판정하고(§3.5.1 과 같은 원리),
`confusable` 로 연결만 해 둔다. 나머지 9군집은 3단계 매핑 테이블이 좌열로 수렴시킨다.

> **왜 방향까지 적었나**: "하이픈은 붙여 쓰기로 통일"만 읽은 추출기가 `wellbeing`·`passerby`·
> `tradeoff` 를 만들면 §3.5.8 예외조항이 경고한 것과 같은 사고 — **사전에 없는 표제어** — 가
> 다어절에서 재발한다. 방향이 없는 통일 규칙은 통일이 아니라 동전던지기다.

### 3.5.9 부대상황 분사 (`coat unzipped`, `arms folded`)
`very` 삽입도 안 되고 시제·태도 이루지 않아 §3.5.1 로 판정되지 않는다.
**보어적 상태 서술로 보아 `pos: adjective` / `lemma`=분사형 / `inflection: base` 로 통일한다.**

## 4. `tier` — 수록 등급 (전부 추출하되 등급으로 노출을 제어한다)

| tier | 기준 | 예 |
|---|---|---|
| `basic` | 중학 수준·초고빈도 기능어. **수록은 하되 학습 큐에는 기본 제외** | the, make, good |
| `core` | 수능 필수. 고교생이 반드시 알아야 함 | quantify, legitimize, inherent |
| `advanced` | 고난도·저빈도지만 기출에 반복 등장 | indefensible, self-deprecating |
| `academic` | 학술·전문 영역 어휘 | capitalist, biographical |

### 「모든 단어」를 두 갈래로 나눠 달성한다 — 이게 이 스펙의 핵심 설계다

목표는 "전 어휘의 완전한 정량 모형"과 "학습 가치 있는 어휘의 완전한 의미 분해"를 **둘 다** 얻는 것이다.
그런데 이 둘은 필요한 도구가 다르다.

| 축 | 대상 | 수단 | 이유 |
|---|---|---|---|
| **정량 모수** | 코퍼스의 **모든 표층형** (23,371종, 출현 634,489회) | **코드 전수 집계** | `the` 가 34,383회라는 사실에 LLM을 태울 이유가 없다. 연도·학년·유형별 출현은 전부 결정론적이다 |
| **의미 분해** | 단어카드가 될 어휘 | **에이전트** | 문맥 의미·한글 뜻·예문·함정은 판단이 필요하다 |

→ **에이전트는 `basic` 기능어(관사·전치사·대명사·be동사·접속사 등 폐쇄부류)를 추출하지 않는다.**
그건 코드가 이미 100% 세고 있다. 에이전트 출력의 30%를 `the`·`of`·`a` 에 쓰는 것은
품질이 아니라 낭비이고, 오히려 정작 중요한 어휘의 분해 밀도를 떨어뜨린다.

`basic` tier 는 **내용어인데 쉬운 것**(make, good, change 같은 고빈도 일반동사·형용사)에만 쓴다.
이런 단어는 다의어 함정이 많아 의미 분해 가치가 크므로 반드시 추출한다.

**애매하면 뽑아라.** 뽑고 등급으로 거르는 것은 되돌릴 수 있지만, 안 뽑은 것은 되돌릴 수 없다.

### 4.1 기능어 처리 — §3 pos 목록과의 충돌 해소

§3 에 `preposition`·`conjunction` 이 살아 있는데 여기서 "폐쇄부류 제외"라고만 하면 충돌한다.
파일럿에서 에이전트 3기가 이 충돌을 동시에 보고했다. 규칙을 확정한다:

**원칙적으로 제외한다. 단 아래 둘 중 하나에 해당하면 반드시 수록한다.**
1. **다의 함정이 실재할 때** — `since`(이래로 / 때문에), `as`(~로서 / ~함에 따라 / ~때문에),
   `while`(동안 / 반면), `for`(위해 / 왜냐하면). 고교생 오독 1순위들이다.
2. **기능어 조합이 하나의 의미 단위를 이룰 때** — `not always`(부분부정), `no longer`,
   `nothing but`, `far from`. 이건 `pos: idiom` 으로 뽑는다.

그 외의 `a` · `the` · `of` · `in` · `and` · `is` · `this` · `he` 같은 순수 문법 기능어는 뽑지 않는다.
빈도는 코드가 이미 전수 집계하고 있다.

### 4.2 밀도 하한 — "대충 뽑고 끝내기" 방지

파일럿에서 "견본 밀도(0.166항목/단어)를 비례 적용하면 짧은 지문의 하한이 깎인다"는 보고가 있었다.
**하한만 정하고 상한은 두지 않는다.**

```
최소 항목 수 = max(12, round(wordCount × 0.15))
```

- 90단어 지문 → 최소 14항목 · 140단어 → 21항목 · 200단어 → 30항목
- 이건 **하한**이다. **상한은 없다.** 학술 지문처럼 어휘 밀도가 높으면 0.3/단어를 넘어도 정상이다.
- 하한 미달로 제출하면 게이트에서 **critical** 이다.

#### 4.2.1 목표 밀도 — 하한은 최저선이지 목표가 아니다 (2026-07-28 실측 추가)

하한만 두었더니 **과소추출이 초록으로 통과했다.** 90단어 지문에서 16항목(0.178)을 낸 산출이
하한 14를 넘겨 통과했는데, 같은 지문의 정상 추출은 28항목(0.311)이었다 — **43%를 놓치고도
게이트가 침묵했다.** 그래서 하한과 별개로 **실측 레퍼런스**를 기준선으로 둔다.

정상 추출 334건의 밀도(항목/단어) 실측 분포:

| min | p05 | p25 | **median** | p75 | p95 | max |
|---|---|---|---|---|---|---|
| 0.180 | 0.201 | 0.222 | **0.243** | 0.269 | 0.312 | 0.429 |

- **목표는 `단어수 × 0.24`.** 334건 중 **한 건도 0.18 아래로 내려가지 않았다.**
- 0.18 미만이면 게이트가 `DENSITY_BELOW_REFERENCE`(major)를 띄운다. **반드시 해소하라.**
- 밀도를 trap 으로 채우지 마라 — §7.1 의 trap **25%** 상한이 그대로 살아 있다(2026-07-29 하향).
  **밀도는 항목 수로 채우는 것이지 함정 수로 채우는 것이 아니다.**
- ⚠️ 이 레퍼런스에는 아직 고3·220단어 이상 표본이 없다. 채워지면 재산출한다.

**놓치기 쉬운 범주** — A/B 대조에서 체계적으로 빠지는 것이 확인됐다. 마지막에 이 목록으로 재점검하라:

1. **다의 기능어** — `since` `as` `while` `for` `just` `yet` `still` `once` `only`. §4.1 이 명시적으로 뽑으라고 한 것들이다.
2. **구동사·숙어** — 동사+전치사는 전부 `phrasal_verb`(§3.5.3). 축자 해석이 안 되는 것.
3. **쉬운데 다의인 내용어** — `make` `take` `tell` `show` `object` `hold` `run` `draw` `leave` `touch` `edge` `order` `matter`. 학생이 1번 뜻으로 읽고 지나간다.
4. **파생어** — 어근은 아는데 접사로 품사·의미가 바뀐 것.
5. **명사+명사 collocation** — 형용사+명사는 각각 분해(§3.5).

### 4.3 그 외 제외 대상
- 고유명사(인명·지명·기관명) — `entry` 로 뽑지 않는다. 단 `example` **문자열 안에** 포함되는 것은
  정상이다(원문을 잘라내야 하므로). `confusable` 에 참고로 적는 것도 허용한다.
- 숫자·기호
- 감탄사

## 5. `senseKo` / `senseEn` 작성 규범 — **의미 병합의 성패가 여기 달렸다**

같은 단어가 4,537개 지문에 흩어져 있고, 서로 다른 에이전트가 각자 한글 뜻을 쓴다.
"수치화하다" / "정량화하다" / "수로 나타내다" 는 **같은 뜻인데 글자가 다르다.**
후속 병합 단계가 이걸 합치려면 다음을 지켜야 한다.

**`senseEn` 이 병합의 1차 판정 근거다.** 한글은 표현이 발산하지만 영영 정의는 수렴한다.
반드시 **완전한 영영 정의문**으로 쓴다. 단어 하나로 때우지 마라.
- ✅ `"to express or measure something as a quantity or number"`
- ❌ `"measure"` / `"quantify (v.)"`

**`senseKo` 규범**

> ⚠️ **이전 판의 "가장 흔한 사전적 대응어"가 §9 검수 항목("사전 1번 뜻을 기계적으로 붙이지 않았는가")과
> 정면 충돌한다는 보고가 파일럿에서 4기에게서 나왔다.** 아래로 확정한다.

**기준은 "그 단어의 사전 1번 뜻"이 아니라 "이 문맥에서 성립하는 sense 의 가장 흔한 대응어"다.**
먼저 문맥에서 어떤 sense 인지 확정하고, **그 sense 안에서** 가장 평범한 한국어를 고른다.

- `failure to help` → sense 는 '하지 않음'이다 → `불이행` (`실패` ❌ — 다른 sense 다)
- `has scientific merit` → sense 는 '근거의 타당함'이다 → `타당성` (`장점` ❌)
- `separate professional from commercial` → sense 는 '개념적 구별'이다 → `분리하다` ✅ (이 경우엔 1번 뜻과 일치)

sense 를 확정한 뒤에는 **그 안에서 창의성을 발휘하지 마라.** 문학적 의역·수사적 표현 금지.

그 외:
- 품사에 맞는 형태로: 동사는 `~하다`, 형용사는 `~한`, 명사는 명사형. **수동태여도 능동형으로**(§3.5.2).
- 길이는 **1~12자**. (파일럿에서 `길`·`층`·`쪽` 같은 1음절 정답어가 하한 2자에 막혀
  `경로`·`층위` 로 우회하는 왜곡이 발생했다. 하한을 1자로 낮춘다.)
- 설명문 금지. 설명은 `senseEn` 과 `trap.note` 가 맡는다.
- 동의어를 `/` 로 나열하지 마라. **하나만** 고른다. (`수치화하다/계량화하다` ❌)
- 물결표(`~`)는 **슬롯 표시가 필요할 때만** 쓴다. 국어사전 표준 표기이므로 금지하지 않는다.
  - ✅ `비록 ~이지만`(although) · `~인 듯하다`(seem) · `~함에 따라`(as) · `~하게 하다`(사역 make)
  - ❌ `~사용하다` 처럼 슬롯이 없는데 붙이는 것
  - 길이 1~12자는 **물결표를 뺀 실질 글자 수**로 센다.
- 문맥 특수성은 `senseKo` 가 아니라 `trap.note` 에 쓴다.

**금지 — 지문이 있어야만 성립하는 소재어를 `senseKo` 에 넣지 마라 (2026-07-29 실측 추가)**

위 조항("문맥 특수성은 `trap.note` 소관")의 적용 예시다. 아래 셋은 실측 적발분이다:

| 표제어 | ❌ 지문 소재가 박힌 뜻 | ✅ 지문 없이도 서는 뜻 | 지문이 준 것 |
|---|---|---|---|
| `housing` | 주거**비** | **주거** | 비용 이야기는 문장이 했다 |
| `upgrade` | **상위 기종으로 바꾸다** | **개선하다** | 기종 이야기는 목적어가 했다 |
| `member` | **의원** | **구성원** | 의회는 수식어가 했다 |

판별법: **그 한국어 뜻을 다른 지문의 같은 sense 에 가져다 놓아도 말이 되는가?**
`주거비`는 임대료 지문에서만 서고, `의원`은 입법부 지문에서만 선다 — 그러면 그건 단어의 뜻이 아니라
**그 문장의 요약**이다. 4단계 병합에서 이런 뜻은 일반 클러스터와 만나지 못하고 혼자 남는다.
지문이 준 한정은 `trap.note` 에 적고, `senseKo` 는 사전이 실을 만한 말로 남겨라.

**한글 표기가 에이전트마다 갈리는 것은 정상이고 예상된 일이다**(파일럿 실측 22.3% 불일치).
그래서 `senseEn` 이 존재한다. 억지로 통일하려 하지 말고, 위 규범만 지켜라 —
정준화는 후속 병합 단계가 `senseEn` 을 근거로 수행한다.

### 5.1 자기정합 — 한 항목의 네 축은 같은 하나의 sense 를 가리켜야 한다

파일럿 적대검수에서 **12건**이 자기모순으로 적발됐다. `professionalism` 은 `senseKo`=직업의식인데
`senseEn` 은 '관계'를 정의했고 문장 해석도 '직업적 관계'였다. 학생 카드에는 뜻과 "그 뜻이 아니다"가
동시에 뜬다.

`senseKo` · `senseEn` · `trap.note` · `sentences[sentenceIndex].ko` — **이 넷은 같은 sense 여야 한다.**

1. **`trap.note` 안에서 `senseKo` 를 부정하지 마라.** 부정하고 싶으면 `senseKo` 를 그 note 가
   지목한 말로 바꿔라. (`senseKo`=세다 / note="동사 measure(재다)" ❌)
2. **`senseEn` 은 `senseKo` 를 영어로 옮긴 것과 같은 sense 여야 한다.**
3. **`senseKo` 와 `sentences[sentenceIndex].ko` 가 같은 말을 가리켜야 한다.**
   (`Consider`=고려하다인데 해석은 "생각해 보라" ❌)

> ⚠️ **3번의 기계 검사(`SENSE_KO_ABSENT_IN_KO`)는 `minor` — 참고 신호일 뿐이다.**
> **이 검사를 통과시키려고 `senseKo` 나 해석을 비틀지 마라.** 한국어 용언은 활용이 어간을
> 삼키므로(줄이+었 → 줄였) 문자열 대조로는 원리상 정확히 판정할 수 없다.
> v3 파일럿에서 이 검사를 맞추려다 실제로 왜곡이 발생했다:
> `lose` 잃다 → 잃어버리다(§3.5.2 가 '잃다'를 정답으로 명시했는데도) · `reduce` 줄이다 → 감소시키다 ·
> `build` 쌓다 → 구축하다 · `touch` 닿다 → 스치다 · `feel` 은 **항목 자체가 삭제**됐다.
> **뜻이 맞다면 이 경고는 무시하라.** 해석은 §1 대로 자연스러운 한국어로 쓰는 것이 우선이다.
> 수동 문장은 해석이 `-되다/-지다` 로 끝나는데 `senseKo` 는 §3.5.2 상 능동이어야 하므로
> **구조적으로 겹칠 수 없다** — 그 경우 경고가 뜨는 것이 정상이다.

### 5.2 `senseEn` 은 지문에서 독립해야 한다

`senseEn` 은 **이 문맥에서 성립하는 sense** 를, **이 지문을 읽지 않은 사람도 이해할 수 있는
사전형 정의문**으로 쓴다. 여기에 지문 흔적이 남으면 그 레코드는 다른 지문과 영원히 병합되지 않는다.

- **(a) 지문 고유 요소를 정의문에 넣지 마라.** `"to let a reader experience something…"` ❌
  (`a reader` 가 박혀 이 지문 전용 클러스터가 된다)
- **(b) 문맥 sense 가 비유·확장이면 그 확장된 뜻을 정의하라.** 문자 뜻을 적어놓고
  `trap` 에서 "비유다"라고 하지 마라. 문자 뜻과의 관계는 `trap.note` 가 맡는다.
- **(c) 한 정의문에 두 sense 를 담지 마라.** 세미콜론·슬래시로 뜻을 나열하면
  병합 단계에서 서로 다른 두 무리가 이 항목을 다리 삼아 잘못 이어붙는다.

  > **`or` 금지는 2026-07-29 에 정정됐다 — 이제 `or` 자체는 금지가 아니다.**
  > 이전 판은 `or` 를 세미콜론·슬래시와 나란히 금지했다. 그런데 실측 `senseEn` 의
  > **42.2%(9,702/22,983)가 `or` 를 쓰고 대부분은 §10.4.1 이 명시적으로 허용한
  > 근접 동의어 이중어**(`to obtain or receive something`)였다. 42%를 형식 위반으로 두면
  > 조항이 사문화된다 — 실제로 기계 게이트는 `or` 를 검사한 적이 없고(세미콜론·슬래시만 본다),
  > 그래서 이 문구는 **검수자만 헷갈리게 하는 죽은 조문**으로 2일간 남아 있었다.
  >
  > **금지되는 것은 이것뿐이다: 문자 뜻과 비유 뜻을 `or` 로 잇지 마라.**
  > - ❌ `"to cut something with a blade or to reduce a budget"` — 두 sense 다. 항목을 둘로 쪼개라(§5.2 말미).
  > - ❌ `"a part of the body or a division of a company"` — 문자/비유가 한 문장에 있다. (b) 위반이기도 하다.
  > - ✅ `"to obtain or receive something"` — 하나의 뜻을 두 말로 적은 것. **정상이다.**
  > - ✅ `"a feeling of worry or fear about something"` — 근접 동의어 이중어. **정상이다.**
  >
  > 판별: **`or` 양쪽이 사전에서 같은 번호로 묶이는가?** 묶이면 이중어, 갈리면 두 sense 다.
  > 이건 §10.2 치환 시험을 정의문 안에 적용한 것과 같다.

- **(d) 정의문 안에서 표제어 자신을 쓰지 마라**(순환 정의).
- **(e) 목적어 삭제 시험 — 정의문에서 지문을 지워라. (2026-07-29 신설)**

  `senseEn` 을 다 쓴 뒤 **한 번 더 읽고, 지문의 주어·목적어·한정어가 그대로 또는 동의어로
  남아 있으면 지워라.** (a)가 "넣지 마라"는 원칙이라면 이건 그 원칙을 강제하는 **절차**다 —
  실측에서 (a)만으로는 막히지 않았다.

  | 표제어 | ❌ 지문이 박힌 정의 | ✅ 지문을 지운 정의 | 무엇이 새어들었나 |
  |---|---|---|---|
  | `member` | `a person who belongs to a legislative body` | `a person who belongs to a group or organization` | 지문의 한정어(→ `senseKo` 까지 「의원」으로 오염) |
  | `get` | `to obtain thoughts or suggestions` | `to come to have something` | 지문의 목적어 |
  | `housing` | `the cost of places where people live` | `places where people live` | 지문의 상위 화제(→ 「주거비」) |

  지운 자리는 **`something`·`someone`·`a group`** 같은 일반항으로 메운다. 정의가 헐거워 보여도
  그게 맞다 — 사전 정의는 원래 헐겁다. 문맥이 준 구체성은 `example` 과 `sentences[].ko` 가
  이미 완전하게 보존하고 있다. **정의문까지 구체적일 이유가 없다.**

  > **이 시험이 가장 급한 이유(2026-07-29 감사)**: 이 결함은 하류 손실이 제일 크다.
  > 지문이 박힌 `senseEn` 은 **4단계 병합에서 일반 클러스터와 영원히 만나지 못한다.**
  > `member`=「의원」은 `member` 의 다른 4,536지문 어디와도 병합되지 않고 혼자 남고,
  > §11.2 에 따라 혼자 남은 sense 는 자기 `senseId` 를 받아 **학생에게 「의원」이라는
  > 단어카드로 출제된다.** 추출 단계의 한 줄이 학습 데이터 끝까지 살아남는다.

**한 단어가 한 지문에서 두 번 다른 뜻으로 쓰였으면 항목을 두 개 만든다.**
같은 뜻으로 여러 번 쓰였으면 **가장 대표적인 1회만** 항목으로 만든다.

## 6. 예문 규범

- `example` 은 **지문 원문에서 그대로 잘라낸다.** 다듬거나 줄이거나 문법을 고치지 않는다.
- **중복 예문은 정상이다.** 한 문장에서 5개 단어가 나오면 5개 항목이 같은 `sentenceIndex` 를 갖는다.

### 6.1 예문과 해석이 어긋나면 카드가 깨진다

학생 화면에는 `example` 과 `sentences[sentenceIndex].ko` 가 **나란히** 뜬다.
파일럿 실측 **151/255(59.2%)** 가 "예문은 5~9단어 조각인데 해석은 문장 전체 번역"이었다.
극단적으로 `phony` 는 예문이 1단어인데 해석은 46자 문장 전체였다. 학생은 그 긴 해석이
이 조각의 뜻이라고 오인하거나 대응을 포기한다.

| 문장 길이 | `example` | `exampleKo` |
|---|---|---|
| **40단어 이하** | **문장 전체를 그대로 쓴다. 자르지 마라.** | `null` (해석은 `sentences[].ko` 가 담당) |
| 40단어 초과 | 절 단위로 잘라도 된다. **최소 5단어 + 주어·동사 포함** | 그 절에 대응하는 **한글 조각**을 반드시 채운다 |

즉 자르는 것은 예외이고, 자를 때는 해석도 같이 잘라 넣는다.
잘린 `example` 은 여전히 §2-불변식 2(연속 부분문자열)를 지켜야 한다.

## 7. `difficulty` / `trap`

`difficulty` 1~5 **초안**이다. 최종값은 후속 정량화 단계가 빈도·학년 분포·문맥 복잡도를
합쳐 재계산한다. 여기서는 "고교생 체감 난이도"를 솔직하게 적으면 된다.

### 7.1 **함정 없음이 기본값이다**

파일럿 실측: 255항목 중 **186건(72.9%)** 에 trap 이 달렸고 견본은 84.4%였다. 대부분이 오독 위험 0인
사후 설명이었다. 실재하는 함정(`merit`·`certain`·`failure to`·`causal`)의 품질은 높았으므로
처방은 "더 달아라"가 아니라 **"깎아라"** 다.

> **한 지문의 trap 비율이 25% 를 넘으면 게이트가 반려한다.** (2026-07-29: 50% → 25%)

#### 왜 50% 를 25% 로 내렸나 (2026-07-29 전수 실측)

**50% 상한은 아무것도 막지 못했다.** 724파일 전수 측정:

| 지표 | 실측 |
|---|---|
| 전 코퍼스 trap 비율 | **37.0%** (8,494/22,983) |
| 50% 상한에 걸린 파일 | **0건 / 724** |
| 파일별 trap 비율 분포 | p05 0.259 · p25 0.333 · **median 0.375** · p75 0.414 · p95 0.457 · **max 0.500** |

**최댓값이 정확히 0.500 이다.** 이것이 결정적이다 — 상한이 이상치를 걸러내는 천장이 아니라
**생성이 겨냥한 과녁**으로 작동했다는 뜻이다. 파일들은 상한 바로 아래에 촘촘히 눌려 있고
아무도 넘지 않는다. **상한을 주면 그 상한까지 채운다.**

**25% 라는 숫자의 근거**(임의로 고른 것이 아니다): 2026-07-29 감사에서 검토한 함정 70개 중
**29개(41.4%)가 가짜**였다. 가짜를 걷어낸 뒤의 예상 실질 trap 비율은
`37.0% × 58.6% = 21.7%` 다. 25% 는 그 위에 놓인 가장 가까운 방어선이다.

가짜 41.4% 를 걷어냈다고 가정하고 파일별로 재계산하면:

| 상한 | 걸리는 파일 |
|---|---|
| 현행 50% | 0건 (지금도, 정화 후에도) |
| **25%** | **129건 / 724 (17.8%)** ← 실제로 무언가를 잡는다 |
| 30% | 0건 |

25% 는 **정화된 코퍼스도 통과시키되 함정 과잉 파일은 잡아내는** 유일한 구간이다.
30% 로 하면 다시 0건이 되어 50% 와 똑같은 장식이 된다.

> ⚠️ **이 상한은 상한이지 목표가 아니다.** §4.2.1 이 밀도에서 겪은 것과 같은 함정이 여기 있다 —
> 25% 를 채우려고 함정을 만들지 마라. **§7.2.1 3단 시험을 통과한 것만 남기면 자연히 그 아래로 내려간다.**
> 비율을 맞추려고 §7.2.1 을 느슨하게 적용하는 순간 이 개정 전체가 무의미해진다.

**적용 순서 — 이 상한만 먼저 켜지 마라.** 현재 산출물은 **695/724(96.0%)가 25% 를 넘는다.**
§7.2.1 개정본이 추출기에 도달하기 전에 게이트를 켜면 파일 96% 가 빨간불이 되고,
**함정을 지우는 것만으로 통과시키려는 압력**이 생긴다 — 그러면 이번엔 진짜 함정이 삭제된다.
(§5.1-c 에서 검사를 맞추려고 뜻을 비틀었던 것과 같은 압력이다.)

> **순서: ① §7.2.1 개정본을 추출기·검수자가 읽는다 → ② 재추출·수정 → ③ 25% 게이트를 켠다.**
> 25% 는 **정화의 결과를 확인하는 자**이지 정화를 수행하는 도구가 아니다.

### 7.2 배제 규칙 5종 — trap 을 달기 전에 전부 통과시켜라

| # | 배제 | 이유 |
|---|---|---|
| ① | **형태소 분해는 함정이 아니다** (`un-`+`able`, `mind`+`less`) | 이건 정보지 오독 위험이 아니다. `confusable` 로 처리하라. `negation` 은 **접두사가 없었어도 문장이 성립해 학생이 뒤집힘을 놓치는 경우**(`indifferent`, `invaluable`, 부분부정)에만 쓴다 |
| ② | **발음·강세·동음이의 근거 무효** | §1 대로 이 코퍼스는 **음성 자료가 없는 읽기 자료**다. 학생은 소리를 듣지 않는다 |
| ③ | **자기무효 함정** — note 에 `관사 the 가 붙었으므로`·`앞에 this 가 있으므로` 같은 **지시사·관사 해소 단서**를 스스로 적었다면 | 문맥이 이미 해소한 것은 함정이 아니다. `trap: null` 로 내려라.<br>단 **구문 환경 제시는 자기무효가 아니다** — `a certain + 명사 형태에서는` 처럼 학생이 알아야 할 판별 근거는 적어도 된다 |
| ④ | **저빈도어와의 혼동** (`canvases`↔`canvass`, `scarcity`↔`scary`) | 혼동은 **학습자가 둘 다 아는 단어 사이에서만** 성립한다. `confusable` 로만 남겨라 |
| ⑤ | **"어원이 같지만 뜻이 다르다"** | 사후 설명이지 오독 시나리오가 아니다 |

### 7.2.1 최종 관문 — **3단 반증 시험** (2026-07-29 전면 교체)

> **이전 판의 최종 관문은 폐기됐다.** 그것은 이렇게 적혀 있었다:
> *"`trap.note` 의 첫 문장에 「학생이 X 로 읽어 Y 를 놓친다」는 실제 오독 시나리오를 써라.
> 그 문장을 못 쓰면 `trap: null` 이다."*
> **이 관문은 문장을 쓸 것만 요구했고, 문형만 채우면 자동 통과였다.** 아래가 그 대가다.

`trap` 을 달려면 note 를 쓴 뒤 **세 줄을 나란히 적어 스스로 반증을 시도하라.
하나라도 실패하면 `trap: null` 이다.** 통과한 것만 남긴다.

| # | 시험 | 묻는 것 | 실패 예 |
|---|---|---|---|

#### 왜 관문을 통째로 갈았나 (2026-07-29 감사)

검토한 함정 **70개 중 29개(41.4%)가 가짜**였다. **기계 게이트는 그중 0건을 잡았다.**

가짜가 생긴 경로는 부주의가 아니라 **관문의 설계**다. 옛 관문은 *"「학생이 X 로 읽어 Y 를 놓친다」는
문장을 쓸 것"* 만 요구했다. 그러면 그 문형을 채우는 가장 싼 방법은 **판단이 아니라 복사**다.

> **실측 증거**: lemma `even` 의 trap 21건 중 **11건(52%)이 「평평한/짝수의」라는 동일한 오독**을 쓴다.
> 그런데 이 코퍼스의 `even` 은 **47건 중 46건이 부사 자리**다 —
> **형용사 독해가 통사적으로 불가능한 자리**에 형용사 오독을 11번 적었다.
> 지문을 본 판단이라면 이런 일이 일어날 수 없다. **문형을 복사한 것이다.**

가짜의 두 유형 — 3단 시험은 정확히 이 둘을 겨냥한다:

1. **통사적으로 불가능한 오독** → **(i)이 잡는다.**
   `even`+to부정사 앞 「평평한」 · `a former`+명사 앞 「전자」 · `did so` 뒤 쉼표에 「매우」 · `office`=「직위」
2. **오독해도 같은 말에 도달** → **(ii)가 잡는다.**
   `pioneer` 개척자=선구자 · `filter` 걸러내다=걸러내다 · `produce` 생산하다 ·
   `open` 식당을 열다=개업하다 · `make` 만들다 · `way` 길 · `nearly` 가까이

> ## 교훈: **형식을 검사하면 형식만 채워진다.**
>
> **이 프로젝트는 같은 사고를 이미 한 번 겪었다.** §5.1-c 의 `SENSE_KO_ABSENT_IN_KO` 검사가
> 「`senseKo` 어간이 해석에 나타나는가」라는 **형식**을 봤더니, 에이전트가 검사를 맞추려고
> **뜻을 비틀었다** — `lose` 잃다→잃어버리다, `reduce` 줄이다→감소시키다, `build` 쌓다→구축하다,
> `touch` 닿다→스치다, `feel` 은 **항목 자체가 삭제**됐다. 그래서 그 검사는 `minor` 로 강등됐다.
>
> 옛 §7.2 최종 관문은 **똑같은 오류를 반대 방향으로** 저질렀다. 그때는 형식 검사가 내용을 왜곡했고,
> 이번엔 **형식 요구가 내용을 대체했다.** 둘 다 뿌리는 하나다 —
> **"무엇을 쓸 것인가"를 요구하면 그 형식이 채워질 뿐, 그것이 참인지는 아무도 묻지 않는다.**
>
> 그래서 새 관문은 **쓸 문장을 지정하지 않는다. 자기 주장을 깨뜨려 보라고 요구한다.**
> (i)(ii)(iii)은 채울 칸이 아니라 **반증 시도**다. 반증에 실패해야 통과다.
>
> **다음 개정자에게**: 이 관문을 다시 「~라고 써라」 형태로 되돌리지 마라.
> 그 형태는 2026-07-29 에 41.4% 가짜율로 실패했다.

#### 이 관문은 왜 기계 게이트가 아닌가 (되돌리기 방지 기록)

"그러면 3단 시험도 코드로 검사하면 되지 않나"는 제안이 반드시 나온다. **시도했고, 안 된다.**

(ii) 도달점 시험을 기계화해 봤다 — note 에서 「'X'로 읽어」의 X 를 뽑아 `senseKo` 와 대조하는 검출기다.
**8,548건 중 89건(1.0%)만 걸렸고, 그중 상당수가 오탐이었다**(`nest` 「둥지」→「둥지를 틀다」,
`woman` 「여자」→「여자를 배치하다」는 **진짜** 품사 함정인데 문자열이 겹쳐서 걸린다).
실제 가짜율 41.4% 에 대해 **재현율 1.0% · 정밀도 미달** — 게이트로 쓸 수 없다.

(i)(iii)은 그 자리의 통사 가능성과 학년별 뜻 순위를 알아야 하므로 **원리상 문자열 검사로 판정되지 않는다.**

> **따라서 이 관문은 §9 「에이전트 검수」가 지키는 유일한 방어선이다.**
> 기계가 못 잡는다는 사실 자체를 스펙에 남긴다 — 게이트가 조용하다는 것이
> **함정이 건전하다는 증거로 오독되는 것**이 이번 사고의 핵심이었기 때문이다.
> 게이트 통과는 §7.2.1 통과가 아니다.

### 7.3 `trap.kind` 결정 트리 — 위에서부터 순서대로 판정

**전제: §7.2.1 3단 시험을 먼저 통과해야 이 트리에 들어온다.** 여기는 *어떤 함정인가*를 정하는 곳이지
*함정인가*를 정하는 곳이 아니다. 시험을 통과하지 못한 것은 트리에 넣지 말고 `trap: null` 로 끝낸다.

| 순서 | 조건 | kind |
|---|---|---|
| ① | 오독 원인이 **문장 구조**다 — note 에 **도치·부분부정·가주어·목적격보어·대동사·분사구문** 중 하나가 (용어가 아니라 오독 시나리오로, §7.3.1) **명시적으로 기술**될 때만 | `syntax` |
| ② | **다른 단어와 형태가 닮았다** — note 에 그 단어를 명시하고, 그 단어가 고교 학습 범위 안이어야 한다 | `form-confusion` |
| ③ | **한국식 외래어 간섭이다** — note 에 한국어 음차와 통용 의미를 반드시 쓴다 | `false-friend` |
| ④ | **같은 단어의 다른 뜻이다** | `polysemy` |
| ⑤ | **특정 연어에서만 성립한다** | `collocation` |
| ⑥ | **격식·인용부호 거리두기·평가 함의다** | `register` |
| ⑦ | **접두·부정어로 극성이 뒤집혔다**(①~⑥ 아님 + 배제규칙 ① 통과) | `negation` |
| **⑧** | **①~⑦ 어디에도 정확히 맞지 않는다** | **`trap: null`** ← 종결 분기 (2026-07-29 신설) |

`kind` 와 `note` 내용이 어긋나면 검수에서 major 다.

#### ⑧ 종결 분기 — **맞는 칸이 없으면 함정이 아니다** (2026-07-29 신설)

> **①~⑦ 중 어느 것에도 정확히 맞지 않으면 `syntax` 로 보내지 마라. `trap: null` 이다.**

**왜 필요했나**: 이전 트리에는 **종결 분기가 없었다.** ①~⑦ 을 다 훑고도 맞는 칸이 없을 때
갈 곳이 지정돼 있지 않았고, ①`syntax` 가 **트리 맨 위에 있으면서 조건이 가장 헐거웠기 때문에**
(「오독 원인이 문장 구조다」) 잔여물이 전부 그리로 흘러들었다. 실측 `syntax` **959건**.

트리에 종결 분기가 없으면 **분류기는 반드시 어딘가로 흘려보낸다.** 「해당 없음」이라는 출구를
명시하지 않는 한, 애매한 것은 가장 헐거운 칸에 쌓인다. 이건 이 트리만의 문제가 아니라
**모든 결정 트리의 구조적 결함**이므로, 앞으로 트리를 만들 때는 종결 분기를 먼저 적어라.

#### ①`syntax` 는 **구조 오독 전용**이다 — 어휘 뜻 오독을 담지 마라

`syntax` 는 **문장의 짜임을 잘못 읽는 것**이다. 「이 단어를 다른 뜻으로 읽는다」는
아무리 그럴듯해도 `syntax` 가 아니다 — 그건 ④`polysemy` 이고, ④에도 안 맞으면 ⑧이다.

| ✅ `syntax` 가 맞다 (구조가 무너진다) | ❌ `syntax` 가 아니다 (뜻만 틀린다) |
|---|---|
| "학생이 `only` 를 `maintained` 에 붙여 「유지만 된다」로 읽어 수단의 제한을 놓친다" | "학생이 `office` 를 「직위」로 읽는다" → 뜻 오독. ④ 또는 ⑧ |
| "학생이 `found` 를 「찾았다」라는 중심 동작으로 읽어 주체를 잘못 잡는다. 여기서는 `documents` 를 꾸민다" | "학생이 `even` 을 「평평한」으로 읽는다" → 뜻 오독. §7.2.1(i) 에서 이미 탈락 |
| "학생이 앞의 `not` 을 놓쳐 「1년 이상 산다」로 읽어 뜻이 뒤집힌다" | "학생이 `pioneer` 를 「선구자」로 읽는다" → §7.2.1(ii) 에서 탈락 |

판별: **note 를 읽고 「어느 단어가 어느 자리에 걸리는가」가 바뀌면 `syntax`,
「그 단어를 무슨 뜻으로 읽는가」만 바뀌면 `syntax` 가 아니다.**

**구동사(`phrasal_verb`)의 관용 의미는 ⑤ `collocation` 이다.** 트리 순서상 ④ polysemy 로 갈 것 같지만,
전치사가 뜻을 고정한다는 점이 본질이므로 `collocation` 으로 통일한다(`engage in`, `bring about`, `pull over`).

### 7.3.1 `syntax` 함정을 §7.4 금칙 없이 쓰는 법

§7.3① 은 구조 오독을 `syntax` 로 잡으라 하는데 §7.4 는 어법 용어를 금칙으로 막는다.
**금지되는 것은 문법 용어이지 구조 설명 자체가 아니다.** 오독 시나리오로 풀어 써라.

| ❌ 금칙 (용어 강의) | ✅ 허용 (오독 시나리오) |
|---|---|
| "5형식 동사로 목적격보어에 형용사를 취한다" | "학생이 makes 뒤 명사를 목적어로만 보고 뒤의 형용사를 놓친다" |
| "분사구문이 부대상황을 나타낸다" | "학생이 unzipped 를 앞 명사의 동사로 읽어 문장이 둘로 쪼개진다" |
| "가주어 it 이 진주어 to부정사를 받는다" | "학생이 it 을 앞 문장의 무언가로 받아 주어를 잃는다" |

### 7.4 `trap.note` 형식

- **2문장 이내, 100자 이내.** (파일럿 실측 66.1%가 90자 초과, 최대 157자 — 함정 설명이 뜻·예문보다
  화면을 지배해 반복 학습 중에 읽히지 않는다.)
- 담을 것은 둘뿐이다: **(a) 학생이 무엇으로 잘못 읽는가, (b) 여기서는 무슨 뜻인가.**
- **금칙**: 문항 번호·"정답 근거"·"보기" 등 시험지 참조 / 어법 구조 강의(5형식·목적격보어·분사구문) /
  `수미상관`·`미끄러짐` 같은 문학·번역투 용어 / 발음기호(`/…/`)·강세 표기.
- **카드 자립**: note 는 **함께 뜨는 그 문장 하나만으로** 검증 가능해야 한다. 다른 문장을 근거로
  들어야 한다면 그 영어 조각을 note 안에 인용하라 (예: `앞 문장 'readily available' 을 뒤집은 말`).

## 8. 금지사항 (위반 시 critical)

1. **원문 훼손** — 지문 문장을 고치거나 다듬지 않는다.
2. **예문 창작** — 지문에 없는 문장을 만들지 않는다.
3. **키 자유작명** — §2 스키마의 키 이름을 바꾸지 않는다.
4. **숫자 창작** — 빈도·출현 횟수 같은 수치를 추정해 적지 않는다. 그건 코드가 집계한다.
5. **고유명사 수록**.
6. **없는 함정 지어내기**.
7. **다른 지문 참조** — 각 에이전트는 **배정받은 지문만** 본다. 코퍼스 전체를 뒤지지 않는다.
8. **파일 부분 수정** — 항상 전면 교체로 쓴다.
9. **지문 밖 사실 단정** — `trap.note`·`senseEn`·`senseKo` 는 **배정받은 지문 안에서 검증 가능한
   내용만** 담는다. 배경지식이 꼭 필요하면 `(지문에는 나오지 않지만)` 으로 출처를 표시하고,
   **`여기서는 ~다` 라는 단정 문형을 쓰지 마라.**
   - 실제 적발: `third variable` 의 note 가 `"여기서는 '나이'가 제3의 변수다"` 라고 단정했는데
     원문 67단어 어디에도 나이 언급이 없다. 통계학 상식으로는 맞지만 **지문이 제3변수의 정체를
     밝히지 않은 채 끝난다.** 3개 렌즈가 독립적으로 같은 지적을 냈다.
   - 이게 퍼지면 검수자가 지문만으로 진위를 판정할 수 없게 되고, 학생은 카드가 알려준 답을
     지문에서 찾다가 자기 독해를 의심한다.

## 10. 4단계 — sense 병합 규범 (2026-07-28 신설)

3단계 집계는 `senseEn` 문자열이 하나로 수렴한 표제어만 자동 병합한다. 나머지는
`build/merge-worklist.json` 으로 떨어지고, **이 절이 그 판정 규범이다.**

실측(369지문): 표제어 5,221개 중 **1,611개**가 판정 대상, sense 후보 **5,315개**.
후보 수 분포 — 2개 828 · 3개 329 · 4~5개 285 · 6~8개 108 · 9~15개 51 · 16개 이상 10.

### 10.1 이 단계가 존재하는 이유

지문마다 다른 에이전트가 작업하므로 **같은 뜻에 다른 한국어가 붙는다.** 실측 예:

| 표제어 | 후보 A | 후보 B | 판정 |
|---|---|---|---|
| `about`(adv) | 대략 / *used before a number to show that it is not exact* | 약 / *a little more or less than a stated number* | **MERGE** — 사전이 한 뜻으로 싣는다 |
| `make`(verb) | ~하게 하다 / *cause someone to become a particular state* | ~하게 하다 / *cause a person or thing to be in a certain state* | **MERGE** — 표현만 다르다 |
| `as` | 로서 / *in the role of* | ~함에 따라 / *at the same time as something changes* | **SPLIT** — 사전이 다른 번호로 싣는다 |

**문자열·임베딩 클러스터링은 성립하지 않는다.** 파일럿에서 lemma+pos 가 겹친 13쌍 중
`senseEn` 문자열이 일치한 것은 2쌍뿐이었다. 반드시 **예문을 근거로 한 의미 판정**이어야 한다.

### 10.2 판정 기준 — 치환 시험

> 두 후보가 같은 sense 인가?
> **A 의 `senseEn` 을 B 의 예문에 적용했을 때, 고교생이 이해하는 내용이 달라지는가?**
> 달라지지 않으면 **MERGE**, 달라지면 **SPLIT**.

보조 기준 — 이건 **사전이 몇 번으로 싣는가**와 같아야 한다:
- 같은 번호 아래 들어갈 표현 차이(정도·격식·어순) → MERGE
- 다른 번호를 받을 의미 차이(다의·품사전성·비유확장) → SPLIT
- **정의문 말미의 방법·수단 부사구 차이는 같은 번호다** — `help ~ by giving support` 와
  `help ~ by taking part in it` 은 서술 상세일 뿐이다 → MERGE

#### 10.2.1 치환은 **양방향**이다 (파일럿 개정)

한쪽 정의가 다른 쪽의 상위집합이면 한 방향 치환은 자동으로 통과한다
(`keep: in a particular state` ⊃ `at a particular level or in a particular state`).
**A→B 와 B→A 를 모두 시험하라.** 한 방향만 보면 협의 정의를 광의 예문에 넣어 과잉 SPLIT 하거나,
광의 정의로 전부 삼켜 과잉 MERGE 한다.

#### 10.2.2 구문 틀이 다르면 다른 번호를 의심하라 (파일럿 개정)

파일럿에서 **재현 가능한 판정선은 `senseEn` 문구가 아니라 구문 틀이었다.**

| 표제어 | 갈린 기준 |
|---|---|
| `find` | `find + that절`(알아내다) / `find + O + 보어`(여기다) / `be found in + 장소`(존재하다) / `find + O`(찾다) |
| `make` | `make + O + 형용사·명사` / `make + O + 동사원형` |
| `while` | 주어가 다른 병렬 대조 → whereas / 같은 주어를 인정 후 반전 → although |

**단, 구문이 다르다는 것 자체가 SPLIT 근거는 아니다**(§10.3-2 의 구문판).
구문이 다르되 학생이 얻는 내용이 같으면 MERGE 다. 구문은 **동점일 때의 판정선**으로 쓴다.

#### 10.2.3 대동사(경동사) 제동 규칙 (파일럿 개정)

`make` `take` `have` `get` 처럼 **의미를 뒤 명사가 내는** 용법에서는 치환 시험이 구조적으로
실패할 수 없다 — 어떤 후보든 "뒤 명사가 뜻하는 행위를 하다"로 치환하면 항상 이해가 보존되므로
**무한 병합이 정당화된다.** 실제로 파일럿에서 10멤버 클러스터가 이렇게 생겼고 반증 불가였다.

> **제동선: 뒤 명사가 행위·사건 명사일 때만 대동사 클러스터에 넣는다.**
> `money` `friend` `pets` 처럼 사물·사람 명사면 분리한다.

#### 10.2.4 후보 내부가 모순이면 (파일럿 개정)

`senseKey` 는 타동인데 `senseEn` 이 자동으로 적힌 후보가 실제로 나왔다.
**예문이 우선이다.** 예문으로도 안 갈리면 SPLIT 한다(합치는 쪽이 되돌리기 비싸다).
한 예문에 대상 토큰이 두 번 나와 타동·자동이 각각 후보가 된 경우도 있었다 — 이때도 예문 우선.

### 10.3 절대 금지

1. **한국어 표기가 같다는 이유만으로 MERGE 하지 마라.** `~하게 하다` 는 사역 전반에 붙는
   범용 표기라 서로 다른 sense 에도 똑같이 달린다. 근거는 언제나 `senseEn` + 예문이다.
2. **한국어 표기가 다르다는 이유만으로 SPLIT 하지 마라.** `대략`/`약`, `잃다`/`상실하다` 는
   같은 뜻의 다른 표기다. **이 단계의 존재 이유가 바로 이 경우를 합치는 것이다.**
3. **후보를 새로 만들지 마라.** 입력 후보 집합 밖의 sense 를 창작하면 안 된다.
4. **누락 금지.** 모든 입력 `senseKey` 는 정확히 하나의 클러스터에 배정된다(전단사).

### 10.4 클러스터 대표값 선정

| 필드 | 규칙 |
|---|---|
| `senseKo` | **클러스터 전 멤버를 덮는** 표기 중 가장 짧고 자연스러운 사전 표기. 동률이면 `occurrences` 합이 큰 쪽. §5 의 1~12자 규범을 그대로 지킨다 |
| `senseEn` | **지문 독립적이면서 클러스터 전 멤버의 예문을 포괄하는** 정의문. 동률이면 `occurrences` 가 큰 쪽. 지문 고유어·순환 정의가 있는 후보는 대표로 뽑지 마라(§5.2) |
| `examples` | 클러스터에 속한 후보들의 예문을 **전부** 보존한다. **§10.5 스키마 필수 필드이고 기계 게이트가 검사한다.** |

#### 10.4.1 대표값은 클러스터를 **덮어야** 한다 (파일럿 개정)

파일럿에서 반복 적발된 결함이다 — **병합은 옳은데 대표값이 좁아서 뭉갠 것처럼 보인다.**

| 표제어 | 뽑힌 대표 정의 | 못 덮은 멤버 |
|---|---|---|
| `notice` | *by seeing or hearing it* | "you notice you **feel** really good" (내적 감각) |
| `consider` | *before judging or deciding* | "Consider walking, for example" (결정 국면 없음) |
| `develop` | *a feeling, habit, or quality* | 항체 생성 · 평판 |
| `take` | senseKo `걸리다`(3자·5회) | 노력·돈을 쓰는 멤버 |

> **가장 좁은 정의를 대표로 뽑지 마라.** 대표 `senseEn` 은 클러스터 전 멤버의 예문에
> 치환 가능해야 하고, 대표 `senseKo` 도 전 멤버를 덮어야 한다.

**근접 동의어 이중어는 "두 뜻 나열"이 아니다.** `to obtain or receive something` 의 `or` 는
§5.2 가 금지한 두 sense 나열이 아니라 하나의 뜻을 두 말로 적은 것이다. 다만 이런 후보를
대표로 뽑았다면 `why` 에 그 사실을 적어라 — 적대 검수가 그 지점을 집중 검증한다.

#### 10.4.2 같은 표제어 안에서 `senseKo` 중복 금지 (파일럿 개정)

§10.4 의 "가장 짧은 표기"를 문자 그대로 적용하면 `spend` 의 **시간 클러스터와 돈 클러스터가
둘 다 `쓰다`** 가 되어 DB 에서 두 sense 가 구분 불가능해진다.
같은 `lemma|pos` 안에서 클러스터들의 `senseKo` 는 **서로 달라야 한다.**
충돌하면 더 긴 쪽을 택해서라도 구분하라(`보내다` / `쓰다`).

#### 10.4.3 `senseKo` 와 `senseEn` 은 서로 정합해야 한다 (파일럿 개정)

둘을 각각 독립 기준으로 뽑으면 서로 다른 멤버에서 온 대표값이 §5.1 자기정합을 깨뜨린다
(실측: `challenge` 가 senseKo=`난관`(상황)인데 senseEn 은 `…task`(과업)).
**senseKo 를 정한 뒤 그것과 같은 sense 를 가리키는 senseEn 을 고른다.**

### 10.5 산출 스키마

```jsonc
{
  "lemma": "about", "pos": "adverb",
  "clusters": [
    {
      "senseKo": "대략",                       // §10.4 대표값
      "senseEn": "a little more or less than a stated number",
      "memberKeys": ["...", "..."],           // 입력 senseKey 들. 합집합 = 입력 전체
      "occurrences": 8,                        // 멤버 합
      "examples": ["...", "..."],             // ★필수★ 멤버 예문 전부. 게이트가 검사한다
      "why": "둘 다 수치 앞의 어림 표시다. 치환해도 이해가 달라지지 않는다.",
      "reviewed": null                        // 적대검수 후 "upheld" | "split-back" 로 채워진다
    }
  ],
  "observations": []                          // §10.6.2 — 되돌리지 않은 관찰
}
```

`why` 는 **MERGE 든 SPLIT 이든 항상** 적는다. 이것이 적대 검수의 입력이다.

> **`examples` 는 권고가 아니라 필수다 (파일럿 개정).** §10.4 가 "예문을 전부 보존한다"고
> 규정했는데 스키마에 필드가 없어 **산출 17개 중 16개가 예문을 통째로 버렸다.**
> 예문은 적대 검수의 유일한 근거이자 학생 카드의 본문이다. 규범과 스키마를 일치시킨다.

> **`reviewed` 가 있어야 "반증 실패로 유지된 병합"과 "아직 미검수인 병합"이 구분된다.**
> 이게 없으면 다음 라운드가 이미 검증된 것을 다시 검증한다.

### 10.6 적대 검수 (병합은 되돌리기 비싸다)

클러스터 수가 입력 후보 수보다 **줄어든 표제어**(= 실제로 병합이 일어난 건)는
**별도 검수자**가 반증을 시도한다. 검수자 프롬프트는 다음을 지킨다:

- 기본 자세는 **반증**이다. "이 병합이 서로 다른 사전 뜻을 뭉갰음을 보여라."
- 불확실하면 `refuted = true`(= 병합 취소, 분리 유지)가 기본값이다.
- **단, §10.3-2 를 근거로 반증하지 마라** — 한국어 표기가 다른 것 자체는 반증 근거가 아니다.
  반증하려면 **예문에서 실제로 이해가 달라진다는 것**을 보여야 한다.

#### 10.6.1 되돌림은 **멤버 단위**다 (파일럿 개정 — 가장 중요한 개정)

초판은 조치를 "클러스터 통째 유지" 또는 "멤버별 전면 분해" 둘로만 뒀다. 그 결과:

> 15멤버 중 **1개만** 잘못 편입됐는데, 되돌리면 **명백히 옳은 병합 13건까지 파괴된다.**
> 그래서 검수자가 **반증을 포기했다.** 실측 사례: `find` 의 `be found in + 출처` 멤버가
> 「찾다」 클러스터로 갔는데 되돌릴 수단이 없어 그대로 뒀다.
> `face` 는 3멤버 중 1개만 문제였는데 나머지 2개까지 강제로 쪼개졌다.

**허용 조치 3종:**

| 조치 | 언제 | 기록 |
|---|---|---|
| `uphold` | 반증 실패 | `reviewed: "upheld"` |
| `move` | 특정 멤버가 **다른 기존 클러스터**에 속한다 | 그 `senseKey` 를 옮기고 양쪽 `why` 갱신 |
| `split-back` | 특정 멤버가 **어느 클러스터에도 안 맞는다** | 그 `senseKey` 만 떼어 새 클러스터로 |

**되돌림 단위는 `senseKey` 다.** `lemma|pos` 단위로 기록하면 부분 되돌림을 표현할 수 없다.

> **되돌린 뒤에는 대표값을 다시 뽑아라 (2차 개정).** 파일럿에서 적대검수가 되돌린 3건 중
> `change|verb`·`face|verb` 두 건이 **§10.4.2 senseKo 중복**을 만들었다 — 쪼개면서 양쪽이
> 원래 클러스터의 대표 표기(`바꾸다`·`직면하다`)를 그대로 물려받았기 때문이다.
> 되돌리기는 멤버 재배치이므로 **§10.4 대표값 선정을 그 클러스터들에 대해 다시 수행해야 한다.**

#### 10.6.2 되돌리기 전에 확인하라 (파일럿 개정)

"불확실하면 되돌린다"는 **되돌리기가 언제나 안전하다**고 전제한다. 성립하지 않는 경우가 있다:

> `challenge`(noun) 에서 의심한 구별(자발적 '도전' vs 닥친 '난관')이 **입력 senseKey 경계와
> 어긋나** 있었다 — 멤버 하나가 두 용법을 이미 품고 있었다. 되돌려도 그 구별은 복원되지 않고
> **정의문 표현 차이만 되살아난다.**

> **되돌리기 전에 "의심하는 구별이 실제로 멤버 경계와 일치하는가"를 확인하라.**
> 일치하지 않으면 되돌리기는 보수적 선택이 아니라 **노이즈 복원**이다.
> 이때는 되돌리지 말고 `observations` 에 기록한다.

#### 10.6.3 되돌리지 않는 관찰도 기록한다 (파일럿 개정)

검수자의 조치 수단이 split-back 하나뿐이면, **되돌릴 수는 없지만 문제인 것**을 보고할 통로가 없다:
- 후보 자체의 `senseEn` 이 오분류로 의심된다(§10.3-3 창작금지에 걸려 손댈 수 없다)
- 사전이 한 번호 아래 하위뜻으로 싣는 SPLIT 의심 건
- **과소병합** — 사실상 같은 정의문이 다른 클러스터로 갈렸다
  (실측: `develop` 의 `gradually gain a quality through effort` 와
  `gradually gain or build up a quality over time` 이 갈렸는데 **어느 게이트에도 안 걸렸다**)

`observations[] = { kind, senseKeys[], what }` 로 남긴다. `kind` 는
`candidate-suspect` · `under-merge` · `sub-sense` 중 하나.

#### 10.6.4 구문이 다르다는 것 자체는 반증 근거가 아니다 (파일럿 개정)

§10.3-2 의 구문판이다. `as` 양태 클러스터는 구문이 두 종류였지만
(`see things as others see them` vs `As Myers observes`) 어느 정의를 어느 예문에 넣어도
학생이 얻는 내용이 같았다. **내용이 달라져야 반증이다.**
이 조항이 없으면 검수자마다 결론이 갈린다.

검수자가 반증한 병합은 되돌린다. 되돌린 건은 `split-back` 으로 기록해 다음 라운드 규범 개정에 쓴다.

### 10.11 개정 — `senseKo` 동일이면 자카드를 요구하지 않는다 (2026-07-30)

**선병합 관문 3개(자카드 · 문법틀 · 한국어표기)를 전부 AND 로 걸었더니, 자명한 패러프레이즈가
대량으로 4단계 LLM 판정으로 넘어갔다.** 58% 시점(지문 2,659건) 실측으로 확인했다.

| 실물 | 후보 | 한국어 뜻 | 차단 사유 |
|---|---|---|---|
| `for example` (idiom) | 30개 | **전부** `예를 들어` | 영어 문구만 달라 자카드 미달 |
| `avoid` (verb) | 31개 | **전부** `피하다` | 같음 |
| `at least` (idiom) | 31개 | **전부** `적어도` | 같음 |
| `purchase` (verb) | 2개 | 둘 다 `구매하다` | "to obtain something by paying money for it" vs "to buy something" — 어휘 겹침 ≈ 0 |

후보 2개짜리 표본 14건 중 **12건이 senseKo 완전 동일 + 영어 문구만 다름**이었다.

→ **같은 `lemma+pos` 에서 `senseKo` 동일은 영어 문구 겹침보다 강한 동일-sense 증거다.**
  `senseKo` 는 애초에 "어느 뜻인가"를 지목하도록 설계된 병합 키다(§5·§10.2).
  그래서 관문 순서를 바꿨다: **문법틀 → 한국어표기 → (모호 글로스일 때만) 자카드.**

**개정 효과 (같은 입력 2,659지문 재실행)**

| | 개정 전 | 개정 후 |
|---|---|---|
| 선병합 흡수 | 15,172건 | **44,048건** (2.9배) |
| sense 후보 | 63,744 | **34,868** (−45%) |
| LLM 판정 표제어 | 8,194 | **5,896** (−28%) |
| 워크리스트 후보 | 52,510 | **21,336** (−59%) |
| 후보당 예문 | 1.45개 | **2.04개** |
| 예문 3개 미만 후보 | 46,810 | **15,620** (−67%) |

**안전장치 — 이 개정은 "합치는 쪽"이라 §10 서두의 비대칭 원칙을 건드린다. 그래서 셋을 둔다.**
1. **문법틀 게이트는 무조건 선행**한다(사역/기동·능동/수동은 어떤 경우에도 안 합친다).
2. **모호 글로스 목록(`KO_VAGUE`)** — `하다`·`되다`·`것`·`만들다` 등 경동사·대동사 계열은
   "어느 뜻인가"를 지목하지 못하므로 병합 키로 못 쓴다. 이때는 자카드를 다시 요구한다.
   (실측: 전부-동일-한국어 2,300 표제어 중 이 목록에 걸린 것 **0건** — 지금은 비용 0의 보험이다.)
3. **무손실** — 병합은 묶음이지 삭제가 아니다. `senseEnVariants` 가 전부 보존되고
   (`avoid`: 59개), 총 출현 수가 보존된다(**100,176 = 100,176**, 전수 확인).

**양방향 검증 (수치가 좋아진 것과 옳은 것은 다르다)**
- 남아야 하는 것(진짜 2의미)이 남았다: `decade` 10년/수십 년 · `for a moment` 잠시/한순간도 ·
  `temporary` 일시적인/임시의 → 셋 다 워크리스트 유지.
- 접혀야 하는 것이 접혔다: `for example` · `avoid` · `at least` · `purchase` → 최종 sense 1개.

### 10.12 병합 축 실측 — 문자열 규칙으로는 못 접는다 (2026-08-01, 3,514파일)

**아무도 안 보고 있던 축이다.** 추출 에이전트는 지문 1건만, 게이트는 파일 1건만, 블라인드
채점자도 지문 1건만 본다. **"같은 단어의 같은 뜻이 지문마다 다른 한국어로 적히는"** 결함은
구조적으로 아무도 못 본다 — 그런데 4단계 병합의 성패와 학생앱 표시 품질이 여기 달렸다.

10회 이상 등장한 자리(`lemma|pos`) 2,827개 · 총 출현 98,235건에서 **자리당 뜻 문자열 가짓수**:

| 축 | 자리당 가짓수 | 정규화 흡수율 |
|---|---|---|
| `senseKo` 원문 | 5.55 | — |
| `senseKo` §10.11 `koCanon` | 5.45 | **1.8%** |
| `senseKo` 더 센 정규화(조사·어미 제거 시안) | 5.32 | 4.1% |
| `senseEn` 원문 | **23.89** | — |
| `senseEn` 정규화 | 23.76 | 0.6% |

**① 축은 한국어가 맞다.** 자리 안의 쌍 445만 건에서 — 한국어만 일치 **35.8%** vs 영어만 일치 **1.4%**.
`senseEn` 은 정의 **문장**이라 표현 자유도가 커서 축으로 못 쓴다(§11 의 senseId 가 senseEn 을
자연키로 쓰지 않는 이유와 같은 뿌리다). §10 의 설계는 옳았다.

**② 그러나 `koCanon` 은 사실상 무력하다(1.8%).** 흔들림이 `하다/되다` 어미나 문장부호가 아니라
**어휘 선택**이기 때문이다 — 문자열 규칙으로 접을 수 있는 종류가 아니다:

```
use[verb]  senseEn 완전 동일  ·  senseKo = 사용하다 / 이용하다 / 쓰다 / 활용하다
attribute[verb]  14회 등장 → 한국어 12가지, 그런데 **전부 같은 뜻**
   귀속시키다 · 탓으로돌리다 · 원인으로돌리다 · ~의것으로보다 · ~의것으로여기다
   · 돌리다 · ~의결과로보다 · 원인으로보다 · ~의탓으로돌리다 · ~에기인한다고보다
```

→ 그래서 **문자열 동일성은 병합의 충분조건일 뿐 필요조건이 아니다.** 같으면 합치고,
다르면 **못 합친다가 아니라 판정이 필요하다**는 뜻이다.
(구현 확인: `vocab-corpus-build.ts:187` 의 `!koSame → return false` 는 영구 차단이 아니라
**4단계 워크리스트로 이관**이다 — 578~580행 리포트가 그렇게 찍는다. 설계는 이미 옳다.

## 11. sense 식별자 — 학습 데이터가 걸리는 지점 (2026-07-28 신설)

### 11.1 문제

3단계 산출의 sense 자연키는 `(lemma, pos, senseKey)` 이고 **`senseKey` 는 영영 정의 문장**이다.
코퍼스가 늘거나 4단계 병합이 돌면 이 문자열은 바뀐다. 그런데 **학생 숙달도가 여기에 걸린다.**

6단계 설계 검수에서 실제 귀결이 나왔다 — 적재기가 재빌드 때 숙달도를 살리려고
**정의문 Jaccard 유사도로 옛 sense 를 새 sense 에 재접합**하는 장치를 만들었고:

- 생존 sense 가 1개인 표제어(**64.9%**)에서는 유사도를 **아예 계산하지 않고** 죽은 뜻 전부를 흡수
- 매핑은 `ON CONFLICT DO NOTHING` 이라 **최초 1회로 고정**되어 재실행해도 정정되지 않는다
- 4단계 병합이 sense 목록을 통째로 교체할 예정이므로, **전혀 다른 뜻에 숙달도가 붙는다**

> 이것은 3단계 선병합이 Jaccard 로 의미를 판정하다 실패한 것과 **정확히 같은 종류의 오류**다.
> 문자열 유사도는 의미 동일성의 근거가 될 수 없다. 그때 폐기한 접근을 여기서 되살리면 안 된다.

### 11.2 규범

> **`senseId` 는 번들 생성 시 부여되고, 한 번 부여되면 절대 바뀌지 않으며, 재사용되지 않는다.**

| 규칙 | 내용 |
|---|---|
| 부여 | 3단계 번들 생성 시 `senseId` 를 발급하고 **`sense-registry.json` 에 영구 기록**한다 |
| 안정성 | 같은 sense 가 다음 번들에도 있으면 **같은 `senseId`** 를 재사용한다. 판정 근거는 **레지스트리에 남은 이전 `memberKeys`(원 추출 항목의 출처 `passageId#index`)** 다 — 정의문 문자열이 아니다 |
| 소멸 | 사라진 sense 는 `retiredAt` 만 찍고 **행을 지우지 않는다.** 학습 데이터는 그대로 붙어 있게 둔다 |
| 병합 | 두 sense 가 합쳐지면 **사람 또는 4단계 LLM 판정이 남긴 명시적 매핑**으로만 잇는다. 코드가 유사도로 추측하지 않는다 |
| 미상 | 매핑 근거가 없으면 **잇지 마라.** 고아 숙달도는 다음 학습에서 자연 소멸한다 — 잘못 이어 붙이는 것보다 낫다 |

**출처 기반 동일성이 문자열 기반보다 안전한 이유**: 추출 항목은 `passageId` + `sentenceIndex` +
`surface` 로 코퍼스에 고정돼 있다. 이건 재빌드해도 안 변한다. 정의문은 변한다.

### 11.2-a 구현 위치와 실측 (2026-07-28 반영)

| 규칙 | 구현 |
|---|---|
| 발급·재사용 | `scripts/vocab-sense-registry.ts` — `SenseRegistry.resolveLemma()` |
| 레지스트리 파일 | 기본 `<lemmas.json 디렉터리>/sense-registry.json`. `--registry=` 로 지정. **없는데 `--apply` 하면 거부**한다(`--registry-init` 로만 첫 세대 발급) — 새 experiments 디렉터리에서 무심코 돌려 전 학생 숙달도를 고아로 만드는 경로를 막는다 |
| 승계 판정 | ① 정의문(정규화)이 그대로면 같은 id ② 아니면 **출처 집합 겹침이 1:1 로 모호하지 않을 때만** 승계. 임계값을 쓰지 않는다 |
| 잇지 않는 경우 | 새 sense 가 옛 항목 2개 이상과 겹침(=병합) / 옛 항목 하나가 새 sense 2개 이상과 겹침(=분할) → 새 id 발급, 매핑 없음 |
| 소멸 | `retiredIn` 만 찍고 항목을 지우지 않는다. 다시 나타나면 같은 id 로 되돌아온다 |
| 자동 alias | **없다.** `vocab_drill_sense_aliases` 는 4단계 판정·사람만 채운다 |

실측(13,783 sense · 6,860 표제어, `scripts/verify-vocab-registry-stability.ts` — DB 접속 없음):

> ⚠️ **분모를 조심하라 (2026-07-29 정정).** 초판 표는 유지율을 **2세대 sense 수** 기준으로 적었다.
> 병합 시나리오는 2세대가 13,783 → 6,860 으로 줄어들므로 분모가 조용히 바뀌어 `100.00%` 가 찍혔지만,
> **학생 숙달도가 걸리는 것은 1세대 `senseId`** 다. 아래는 **1세대 기준**으로 다시 쓴 것이다.

| 2세대 시나리오 | 1세대 senseId 자동 승계 | 은퇴(명시 매핑 필요) |
|---|---|---|
| 동일 코퍼스 재빌드 | **100.0%** (13,783/13,783) | 0 |
| 정의문 전건 재작성(출처 그대로) | **99.94%** (13,775/13,783) | 8 |
| 4단계 병합 시늉(다의어 → 1뜻) | 49.8% (6,860/13,783) | 6,923 |
| 병합 + 정의문 재작성 | **32.3%** (4,451/13,783) | 9,332 |

**이 수치는 실패가 아니라 설계다.** 코드는 병합을 **추측하지 않는다**(§11.2) — 병합된 sense 의
숙달도는 **4단계가 남긴 명시적 매핑**(`memberKeys`)으로 잇는다. 자동 승계율이 32%라는 말은
**나머지 68%가 그 매핑에 의존한다**는 뜻이다.

> **따라서 4단계 산출의 `memberKeys` 는 학습 데이터의 생명줄이다.**
> §10.3-4 전단사 게이트가 지키는 것이 결국 이것이다 — 거기서 senseKey 하나가 빠지면
> 그 뜻에 붙은 학생 숙달도가 이어질 근거가 사라진다.

구 Jaccard 장치는 이 32%와 68%를 구분하지 않고 **전부 자동으로 붙였다** — 그것도
생존 sense 가 1개인 표제어(64.9%)에서는 유사도 계산조차 없이.

### 11.3 이 규범이 미루는 것

**코퍼스가 완결되기 전에는 번들을 확정하지 마라.** 현재 12%(536/4,537)이고 4단계 병합이
2,409 표제어를 대기 중이다. 이 상태에서 `senseId` 를 발급하면 대부분이 곧 은퇴한다.

→ **콘텐츠 테이블 DDL 은 지금 확정해도 되지만, 적재는 추출·병합 완료 후에 한다.**
   그때 발급하는 것이 첫 세대 `senseId` 이고, 그 시점부터 위 안정성 규칙이 적용된다.

## 12. 게이트 운용 규범 — 계기를 데이터보다 먼저 의심하라 (2026-07-30 신설)

이 절은 규범이 아니라 **감독 절차**다. 게이트가 뭔가를 보고했을 때 무엇을 먼저 확인해야
헛수리(코퍼스 오염)를 피하는지 적는다. 둘 다 실측 사고에서 나왔다.

### 12.1 major/critical 보고를 받으면 **수리 지시 전에 오탐률을 손으로 재라**

【실측 2026-07-30】 `ADJ_NOUN_PAIR_MISSING` 이 major 21건을 보고했다. 21건을 열어보니
**11건이 오탐**이었다:

| collocation | 게이트가 요구한 "짝 명사" | 실제 |
|---|---|---|
| `different from` | `from` | 전치사 |
| `natural to` / `enough to` / `suitable to` / `subject to` | `to` | 부정사·전치사 |
| `packed with` | `with` | 전치사 |
| `clothed in` / `inherent in` | `in` | 전치사 |
| `full of` / `characteristic of` | `of` | 전치사 |
| `crucial for` | `for` | 전치사 |

원인은 검사식이 `collocation` 두 번째 토큰을 `/^[A-Za-z][A-Za-z-]*$/` 로만 걸러 **전치사를
명사로 오판**한 것이다. 이 상태로 "짝 명사를 뽑아라"고 지시했으면 에이전트들이
`from`·`to`·`with` 를 표제어 항목으로 만들어 코퍼스를 오염시켰다 — §7.1(함정 비율)에서
이미 한 번 밟은 **"게이트를 맞추려고 데이터를 비트는"** 실패 유형의 재발이다.

→ **폐쇄집합 `ADJ_PAIR_NON_NOUN`** 을 추가해 전치사·접속사·부정사 `to` 를 짝 명사 자리에서
  제외했고, 셀프테스트에 대조군 "형용사+전치사(2토큰)는 면제인가"를 박았다(22/22).
  진짜 결함은 10건(`health`·`writer`·`science`·`job`·`skill`·`change`·`history`·`service`·
  `thing`·`name`)뿐이었다.

**절차**: 새 검사가 처음 보고하는 건수는 **전수 육안 확인**한다. 오탐률을 모르는 채
수리 함대를 보내면, 함대는 게이트를 초록으로 만들 뿐 코퍼스를 나쁘게 만든다.

### 12.2 `--dir` 전량 게이트는 **추출이 도는 동안 찢어진 상태를 읽는다**

【실측 2026-07-30】 전량 게이트가 `critical 6` 을 보고했다. 파일별로 다시 재니 **5건**이었다.
사라진 1건(`2014_SN_3022251_B-q24#1 CONFUSABLE_SELF "successfully"`)은 데이터 문제가 아니었다 —
추출 에이전트가 **자기검증으로 그 결함을 고쳐 파일을 덮어쓴** 것이고, 전량 게이트가 그
사이의 버전을 읽었다(파일 mtime 이 게이트 실행 시각과 겹친다).

→ **전량 게이트 수치는 추출 중에는 근사값이다.** 보고된 critical/major 파일은 반드시
  `--file=` 로 **한 번 더 개별 재검증**한 뒤에야 수리 대상으로 확정한다. 개별 재검증은 싸고,
  이 한 단계가 "이미 고쳐진 것을 다시 고치라고 지시하는" 낭비를 막는다.

### 12.3 산출을 비교할 때 **한쪽만 세지 마라** — 흔들림이 회귀로 보인다

【실측 2026-08-01】 재추출 스테이지 한 파일(`2012_SN_3001002-q24`)을 구본과 나란히 읽었더니
다의 전치사 `for` 두 개(`~에 대해`·`~동안`)가 함정째로 사라져 있었다. §2.5-① 이 코퍼스의
핵심이라고 못박은 바로 그 범주다. 회귀로 판단하고 **"기능어 함정을 잃으면 교체 거부"**
가드를 만들려던 참이었다.

전수로, **양방향으로** 다시 쟀다(65쌍):

| 지문당 | 구본 | 신본 | |
|---|---|---|---|
| 항목 | 41.1 | 39.7 | −3% |
| 함정 보유 자리 | 4.98 | 5.74 | **+15%** |
| └ 기능어 함정 | 1.06 | 1.27 | **+20%** |
| 관용·구동사 | 4.56 | 4.68 | +3% |

함정 이동: 전체 **소멸 160 ↔ 신설 210(순 +50)** · 기능어 **소멸 31 ↔ 신설 45(순 +14)**.
즉 그 `for` 두 개는 **회귀가 아니라 흔들림의 한 사례**였고, 총량은 오히려 늘었다.

**원리**: 같은 브리프를 두 번 돌려도 산출은 흔들린다(§13.4 실측 ~15%). 그래서
**손실 카운트 단독은 언제나 회귀처럼 보인다.** 손실이 회귀인지 흔들림인지는
**같은 축의 획득**을 나란히 놓아야만 갈린다. 이건 §13.4 의 "같은 설정 대조군" 원칙을
집계 축에 적용한 것이다 — 대조군이 없으면 **시간축의 양방향**이라도 세라.

같은 자리에서 두 번째 착시: `advanced` 항목이 지문당 2.92→2.68(−8%)로 보였는데,
자리(lemma+pos) 기준으로는 **소멸 18 ↔ 신설 19 = 순 +1** 이었다. 차이는 한 지문 안의
**같은 자리 다중 의미**를 항목 수가 이중 계상한 것이다. 실물을 읽으니 손실이 아니라 형태 교정이었다 —
`working→workings`, `crystallize→crystallized`, `paralyze→paralyzed`,
`under cover of darkness→under cover of`(재사용 가능한 경계로).

→ **계기**: `node scripts/vocab-compare-corpus.mjs <A디렉터리> <B디렉터리>` 가 이 양방향 대조를
  고정 항목으로 찍는다. 브리프를 고쳤으면 채택 전에 이걸 통과시켜라. **게이트가 아니다** —
  여기 숫자를 브리프에 목표로 넣으면 §5.1-c·§7.1·§7.2-b 의 실패가 다섯 번째로 재발한다.

### 12.4 개정 효과를 시간으로 재려면 **개정 시각으로 갈라라** (2026-08-01)

브리프 개정(§2.6)이 본선에 먹히는지 보려고 raw 를 생성 시각순 10분위로 갈라 결함률을 쟀다.
**평평했다**(파일당 0.13 ~ 0.18, 추세 없음). "최근 6시간 vs 그 이전"도 0.129 vs 0.137 로 같았다.
블라인드에서 −90% 였는데 본선에서 안 움직이는 것으로 읽혀 개정이 무력하다고 판단할 뻔했다.

원인은 데이터가 아니라 **절단점**이었다. §2.6 이 라이브에 들어간 시각은

개정 시각으로 다시 가르니:

|---|---|---|---|---|
| §2.6 이전 | 3,451 | 3,592 | 0.139 | 0.057 |

### 12.4-c ⚠️ **모델을 비교할 때 effort 를 통제하지 않으면 통째로 틀린다** (2026-08-02)

【실측 2026-08-01】 본선 산출에서 구조계열 함정이 sol 1.33 → luna 0.20/지문 으로 떨어진 것을 보고
**"luna 는 sol 보다 구조 함정을 6배 못 잡는다"** 고 결론냈다. 학년까지 통제했고 네 학년 전부
같은 방향이었으므로 확실해 보였다.

**틀렸다.** sol 은 `~/.codex/config.toml` 기본값인 `ultra` 로 돌고 있었고, luna 는 CLI 인자로
`high` 가 주입돼 있었다. **모델이 아니라 사고 수준을 비교하고 있었다.**
같은 지문에서 effort 를 맞춰 다시 재니 luna·ultra 0.86 = sol·high 0.86 으로 **동률**이었다.

이 오독의 대가: v3 브리프를 만들어 채택했다가 되돌리고, luna 산출 434건을 지웠다(복구 불가 —
`experiments/` 는 git 추적 대상이 아니고 Node 삭제는 휴지통을 거치지 않는다).

→ **규칙**: 모델 비교는 **모델 인자와 effort 인자를 둘 다 명시**해서 돌려라.
  `~/.codex/config.toml` 이 조용히 이긴다. 실제로 무엇이 쓰였는지는 **프로세스 인자로 확인**한다:
  `Get-CimInstance Win32_Process -Filter "Name='codex.exe'"` → `-m <모델> ... model_reasoning_effort=<값>`.
  로그 헤더(`모델 <config 기본>`)는 환경변수를 찍을 뿐 실제 모델을 알려주지 않는다.

→ **그리고 삭제는 되돌릴 수 없다.** 산출물을 지우기 전에 **반드시 사용자에게 묻는다.**
  특히 그 산출을 만든 설정이 **사용자가 비용을 이유로 정한 것**이면 그것은 감독의 판단 영역이 아니다.

→ **규칙**: 개정 효과를 시간축으로 잴 때는 **개정 시각을 절단점으로 쓴다.**
  균등 분위·"최근 N시간" 같은 편의 구간은 경계를 가로질러 효과를 희석한다.
  오늘 계기 오독 3건(§12.1 게이트 오탐 · §12.3 한쪽만 세기 · 이 건)이 전부 같은 모양이다 —
  **비교하려는 것으로 실제로 갈리지 않은 두 집단을 비교했다.**

⚠️ **절단점을 `mtime` 으로 "구하지" 마라 — 값으로 못 박아라.** mtime 은 그 뒤 어떤 편집에도
  움직인다(실제로 이 발견 직후 각인 코드를 넣느라 `vocab-extract-codex-v2.sh` 를 고쳤고
  mtime 이 그날 저녁으로 이동했다 — 절단점을 그때그때 구했다면 §2.6 이후 산출 66건이
  전부 다시 "낡음"으로 뒤집혔을 것이다).
  **§2.6 절단점 = `2026-08-01T17:24:02+09:00` (고정).**

### 12.4-b 근본 처방 — 산출물이 **자기 출처를 들고 다니게** 한다

절단점을 못 박는 것은 대증요법이다. 병의 뿌리는 **산출물에 출처가 없다**는 것이다.
`specVersion` 필드가 이미 있었지만 3,533건 전부 `"v3"` 상수라 정보량이 0이었다(견본에서 온 값).

→ 추출 스크립트가 산출 직후 **치환 전 프롬프트 템플릿의 sha1 앞 12자**를 찍는다:
```
briefHash    브리프 판본 지문 — 지문 ID 와 무관하게 판본마다 고정
briefLabel   codex-v2 / codex-v3-struct 등
extractedAt  ISO 시각
```
`node scripts/vocab-stamp-brief.mjs <파일> <해시> <라벨> <시각>` · v2·v3 스크립트 말미에서 호출.
**에이전트에게 시키지 않는다** — 스크립트가 결정론적으로 찍으니 토큰 0·오기 0·누락 0이다.
entries 는 안 건드린다(게이트의 `UNKNOWN_KEY` 는 entries 에만 걸린다, `verify:371`).

음성테스트 4종 통과: 필드 생성·`entries` 보존·게이트 통과 유지 / 없는 파일 무해 /
깨진 JSON 무해(내용 보존 — 게이트가 잡게 둔다).

→ 앞으로 "무엇이 낡았나"는 **`briefHash` 로 판정한다.** `briefHash` 가 없는 파일 = 각인 이전 산출
  = §2.6 절단점 규칙으로 판정. 다음 개정부터는 시간 추정이 아예 필요 없다.

⚠️ **기준 해시를 다른 언어로 재현하지 마라 — 각인과 같은 코드 경로로만 구하라.**
【실측 2026-08-01】 스윕 대상 목록기(Node)에서 heredoc 본문을 잘라 sha1 했더니 `6c19a2073f83`
이 나왔는데 실제 각인은 `318140cb7b63` 이었다(셸 `read -r -d ""` 의 종단 처리가 다르다).
기준이 틀리면 **전량이 "낡음"으로 잡히거나 아무것도 안 잡힌다** — 조용한 대형 오판이다.
→ `bash scripts/vocab-brief-hash.sh` 가 추출 스크립트의 heredoc 구간을 떼어 **같은 셸 코드로** 읽어
  해시를 찍는다. `vocab-stale-list.mjs` 는 `--expect=` 로 **받기만** 하고 추측하지 않는다(미지정 시 종료).
  덧붙여 목록기는 **기준 해시가 산출물 어디에도 없으면 경고**한다 — 브리프를 막 바꾼 직후엔
  정상이지만, 아니라면 기준이 틀렸다는 신호다.

**운용**
```
H="$(bash scripts/vocab-brief-hash.sh)"
node scripts/vocab-stale-list.mjs --expect="$H"        # → experiments/.../sweep-ids.json
bash scripts/vocab-reextract.sh <그 파일> <동시수>       # 스테이징→게이트→가드→백업→교체
```
스윕 목록은 **함정 밀도가 낮은 것부터** 정렬된다 — 중간에 끊겨도 개선 여지가 큰 쪽이 먼저 처리된다.

⚠️ **돌고 있는 셸 스크립트를 편집하지 마라 — bash 는 스크립트를 지연 읽기한다.**
【실측 2026-08-01】 각인 코드를 넣느라 `vocab-extract-codex-v2.sh` 말미(마지막 3줄 → 8줄)를
러너가 도는 중에 고쳤다. 이미 실행 중이던 인스턴스들은 **바이트 오프셋이 밀려** 엉뚱한 지점부터
읽었고 `line 326: RC: unbound variable` 로 죽었다(2건).
피해는 작았다 — 오류가 코덱스가 산출을 **다 쓴 뒤** 마지막 줄에서 났기 때문에 **유실 0**,
종료코드만 더러워졌다. 하지만 편집 위치가 앞쪽이었다면 실행 중인 전량이 깨졌을 것이다.
→ **규칙**: 러너가 도는 중에 추출 스크립트를 고쳐야 하면 (a) **말미에만** 덧붙이거나,
  (b) 새 파일로 쓰고 `mv` 로 원자적 교체하거나, (c) 러너를 멈춘 뒤 고친다.
  고친 뒤에는 반드시 `bash -n` 과 **최근 로그에서 셸 오류 문구 grep** 으로 확인한다.

### 12.7 멱등 검사가 **파일 존재만 보면 껍데기가 영구 결손이 된다** (2026-08-01)

러너들의 재발사 안전장치는 전부 이 모양이다:
```bash
[ -f "$OUT/$ID.json" ] && return 0      # 멱등 — 재발사 무해
```
그런데 이건 **"파일이 있다 = 제대로 뽑혔다"** 를 가정한다. 실행이 중간에 죽어 껍데기가 남으면
그 지문은 **다시는 시도되지 않고**, 총계에는 완료로 잡힌다 — 조용한 영구 결손이다.

【실측】 §12.4-b 의 라이브 편집 창(18:55~19:01)에 이런 파일 2건이 생겼다:
```
{passageId:ebsi_go3_20180711-q36,specVersion:v3,sentences:[],entries:[]}   ← 73바이트, 따옴표 없음
```
게이트를 돌리면 `PARSE_FAIL` critical 이지만, **게이트는 수리 대상을 고를 때만 돌린다.**
그 사이 raw 총계 3,535 는 실제로 3,533 이었다. 진척 보고가 2건만큼 거짓이었다.

→ **계기**: `node scripts/vocab-scan-broken.mjs <디렉터리> [--delete]`
  파싱실패 · 객체 아님 · `sentences` 빔 · `entries` 빔을 찾는다. 기본은 보고만,
  `--delete` 라야 지운다(지워야 러너가 다시 뽑는다). 스테이지 디렉터리에도 쓴다.
  ⚠️ **집필 중인 파일과 죽은 껍데기는 크기로 구분이 안 된다.** 방금 생긴 것은 한 번 더 보고 지워라.

→ **구조 수리**: 멱등 검사를 `[ -f ]` 에서 **"파싱되고 `entries` 가 1개 이상"** 으로 올린다.
  `vocab-reextract.sh` 는 유휴가 되자마자 고쳤다(음성테스트 3종: `{}` · 따옴표 없는 껍데기 ·
  정상본 → 앞의 둘만 재추출로 판정). `vocab-extract-codex-bulk.sh` 는 러너가 돌고 있어 보류다
  (§12.4-b 규칙 — 돌고 있는 셸 스크립트를 편집하지 마라).

### 12.8 동시성은 **올릴수록 총량이 준다** — 실측 (2026-08-01)

| 동시 실행 | 실행당 소요 | 시간당 산출 |
|---|---|---|
| 32 | ~8분 | **243건** |
| 56 (+재추출 24) | ~20분 | 188건 |
| 74 (+구조 A/B 10) | **45~67분** | **81건** |

동시성 2.3배에 실행 시간 6배 — **총량이 3분의 1로 떨어진다.** 코덱스 실행은 CPU·디스크를
많이 쓰고, 이 기계에서 포화점은 **약 32** 다. 그 위로는 서로를 굶길 뿐이다.
같은 포화가 산출 실패로도 나타났다 — 구조 A/B 10기를 얹은 직후 1기가
"파일 읽기 도구가 반복적으로 시간 초과"로 죽었다.

→ **규칙**: 동시 코덱스 실행 총합을 **32 근처로 유지**한다. 부수 작업(재추출·A/B)을 돌리려면
  본선 동시성을 줄여 총합을 맞추지, **더하지 마라.**
  ⚠️ 진행 상황을 `ps | grep -c codex` 로 세지 마라 — 실행 1건이 `codex` + `codex-code-mode-host`
  등 여러 프로세스를 띄운다. **주 프로세스만** 세라(`ProcessName -eq 'codex'`).

→ 잔재 점검(주기적으로): ① **좀비** — 실측에서 48시간·52시간짜리 코덱스 2개가 슬롯을 잡고 있었다.
  ② **중복 모니터** — 정지 탐지기가 4개 돌고 있었고, 그중 옛 판본이 낸 "52건/시간"에 한 번 속았다.

### 12.8-b 러너를 멈췄다 다시 켤 때 — **부모만 죽이면 고아가 남는다**

【실측 2026-08-01】 브리프를 고치려고 러너를 멈출 때 `forever.sh`·`codex-bulk.sh` **부모만** 죽였다.
그 아래 `vocab-extract-codex-v2.sh` 자식 62개가 살아남아 계속 돌았고, 새 라운드 66개가 그 위에
얹혀 **동시 64** 가 됐다 — §12.8 의 과다구독을 스스로 재현했다(산출 20건/시간까지 떨어짐).
게다가 살아남은 고아들은 **옛 브리프**로 계속 뽑고 있었다.

→ **정지는 3계층 전부**: `forever.sh` → `codex-bulk.sh` → `vocab-extract-codex-v2.sh` → `codex.exe`.
  코덱스는 `Stop-Process` 로 안 죽는 경우가 있다(실측: 134개가 그대로 남음).
  `taskkill /F /IM codex.exe /T` 로 확실히 끊고, **0 을 눈으로 확인한 뒤** 재가동한다.
  재가동 전 `vocab-scan-broken.mjs --delete` 로 급종료가 남긴 껍데기를 치우고, 락도 지운다.

→ **장수 러너는 `nohup ... &` 로 띄우지 마라.** 실측: nohup 으로 띄운 `forever.sh` 가
  bulk 를 한 번 발사한 뒤 죽어, 그 라운드가 끝나면 아무도 다음 라운드를 시작하지 않는 상태가 됐다
  (조용한 정지 — 산출은 한동안 나오므로 알아채기 어렵다).
  **하네스 백그라운드 태스크**로 띄우면 몇 시간 안정적으로 살아 있었다(실측). 그쪽을 쓴다.
  반대로 **모니터**는 nohup 이 낫다 — 하네스 태스크 트리를 죽일 때 같이 죽는 걸 2회 겪었다.

### 12.8-c 재가동 시 **환경변수를 기억해야 하는 설정은 언젠가 빠진다** (2026-08-01)

러너를 재가동하면서 `VOCAB_CODEX_MODEL=gpt-5.6-luna` 를 빠뜨렸다. 스크립트 기본값이 비어 있어
`~/.codex/config.toml`(`gpt-5.6-sol` / `ultra`)이 이겼고, **검증하지 않은 모델로 한 라운드가 돌았다.**
실행 시간이 8분 → 18분으로 늘어 처리량이 3분의 1이 됐는데, 원인을 브리프 개정(v3)으로 의심했다.
(짝지은 측정으로 확인하니 v3 는 오히려 11% 빨랐다 — 원인은 모델이었다.)

→ **수리**: `vocab-extract-codex-v2.sh` 의 기본값을 `${VOCAB_CODEX_MODEL:-gpt-5.6-luna}` 로 박았다.
  환경변수는 **실험에서 덮어쓸 때만** 쓴다. 검증된 값은 코드에 있어야 한다.
  일반화: **운용자가 매번 기억해야 하는 설정은 설정이 아니라 사고 예약이다.**

⚠️ **`codex-bulk.sh` 의 라운드 헤더는 환경변수를 찍는다** — 즉 기본값으로 도는 경우
  `모델 <config 기본>` 으로 나와 **실제 모델을 알려주지 않는다.** 실제 확인은 프로세스 인자로 하라:
  `Get-CimInstance Win32_Process -Filter "Name='codex.exe'"` → `-m <모델>`.
  (헤더 문구 수리는 러너 유휴 시. 러너가 도는 중엔 고치지 않는다 — §12.4-b.)

### 12.9 교체 가드가 **더 나은 산출을 버렸다** — 대리지표 실패 5번째 (2026-08-01)

재추출 교체 안전판은 "새 산출의 **항목 수**가 구본의 80% 미만이면 구본 유지"였다.
97건을 교체하며 4건이 이 하한에 걸렸다. 실물로 재판정하니 **2건이 오판**이었다:

| 지문 | 항목 | 함정 | 구규칙 | 실제 |
|---|---|---|---|---|
| `2025_SN_5089362-q41-42` | 81→62 | **4→11** | 거부 | 함정 3배 — 거부가 틀렸다 |
| `2005_YB_5006647-q38` | 34→24 | **2→3** | 거부 | 함정 증가 — 거부가 틀렸다 |
| `2007_06_3001177-q43` | 45→34 | 7→7 | 거부 | 보수적으로 유지(무방) |
| `2025_SN_5089362-q26` | 43→34 | **8→6** | 거부 | 진짜 빈약 — 거부가 옳았다 |

잃은 항목을 읽어보니 `page`(기초어)·`엄지손가락→엄지`(표기 변형)·`index finger` noun→collocation
(품사 재분류)이었다. **스펙은 기초어 채우기를 결함으로 본다(§5·§13).** 그런데 가드는
항목이 많을수록 좋다고 가정하고 있었다 — 스펙과 정반대 방향의 가정을 차단 조건으로 쓴 것이다.

**원인**: 가드의 진짜 목적은 **망가진·잘린 산출**을 막는 것이다. 그런 산출은 항목도 함정도
**같이** 준다. 항목만 보면 "잘린 산출"과 "군살을 걷어낸 좋은 산출"이 구분되지 않는다.

→ **수정**: 항목이 80% 미만이고 **동시에 함정도 늘지 않았을 때만** 구본을 지킨다.
  발사 전 4건에 새 규칙을 적용해 오판 2건만 정확히 뒤집히는 것을 확인한 뒤 집행했다(총 95건 교체).

⚠️ 이것이 이 프로젝트의 **대리지표 실패 다섯 번째**다(§5.1-c · §7.1 · §7.2-b · §12 · 이 건).
앞의 넷은 전부 **추출 게이트**에서 났는데 이번엔 **교체 가드**에서 났다.
→ 규칙을 일반화한다: **"많을수록 좋다"를 가정하는 수치는 어디에서도 차단 조건이 될 수 없다.**
  차단은 "망가졌다"를 직접 가리키는 신호로만 하라(파싱 실패, entries 0, 함정과 항목의 동시 감소).

### 12.5 결함 모집단은 **목록이 아니라 전수 스캔**으로 정한다 (2026-08-01)

1차 재추출 목록(240건)이 결함 파일을 다 담고 있는지 전수로 다시 셌다. 안 담고 있었다 —
**결함 파일 435건 중 목록에 든 것은 33건뿐**이었고 402건이 빠져 있었다.

원인: 목록이 결함 스캔이 아니라 **다른 경위**(감사 표본)로 만들어졌는데, 그 뒤로 "그 목록 = 결함
전량"으로 취급됐다. 결함이 기계로 검출 가능한 종류(§2.6-①: `trap.kind==='collocation'` + 단어
하나 표제어)인데도 전수 스캔을 한 번도 안 돌린 것이다.

→ **규칙**: 수리 대상은 **매번 전수 스캔으로 다시 뽑는다.** 이전 목록을 재사용하지 마라.
  상한(기계로 확실히 아닌 것만 제외)과 하한(기계로 확실한 것만)을 **둘 다** 내고,
  하한을 앞에 배치해 중간에 끊겨도 확실한 것부터 고쳐지게 한다.
  → 2차 목록 `reextract-ids-2.json` = 401건(확정 167 + 의심 234).

### 12.6 **§2.6 이전 산출 전량 재추출 — 확정 (2026-08-01, 사용자 결정)**

결함 스캔으로 뽑은 401건만 고치는 안은 **기각**됐다. 이유는 §13.8 의 블라인드 결과다 —
개선은 `collocation` kind 결함에만 있는 게 아니라 **측정한 네 축 전부**에 걸쳐 있었고
(kindMismatch −90% · fakeTraps −29% · missedStructural −14%, 진 축 없음),
결함 파일만 고치면 나머지 3,050건은 **낡은 브리프 산출로 그대로 남는다.**

**집행 순서 (이 순서를 지킨다)**
1. 잔여 추출 완주 — 1,019건. 재추출과 병행하면 코덱스 경합으로 둘 다 느려지고 실패한다
   (실측: 구조 A/B 10기를 기존 부하 위에 얹었더니 1기가 파일읽기 타임아웃으로 죽었다).
2. **브리프 확정** — §13.9 의 구조 지목 절차(v3) A/B 결과가 나온 뒤에 쓸어야 한다.
   v2 로 3,451건을 쓸고 나서 v3 를 채택하면 그 3,451건이 다시 낡는다.
3. 전량 스윕 — 대상은 **`2026-08-01T17:24:02+09:00` 이전에 생성된 raw 전량**(고정 절단점,

⚠️ 완주 판정은 "스윕을 돌렸다"가 아니라 **낡은 파일이 0건**임을 다시 스캔해 확인한다.

## 13. 추출자 브리프 구성 규범 — 처리량은 브리프 설계로 결정된다 (2026-07-30 신설)

이 절은 어휘 규범이 아니라 **브리프를 어떻게 조립하는가**에 대한 규범이다.
코덱스가 주간 크레딧 소진(→8/6)으로 멈춰 클로드 단독 운용이 되면서 **세션 토큰 한도가 병목**이 됐고,
그때부터 `지문당 토큰`이 곧 `처리량`이다.

### 13.1 파일 읽기는 그 에이전트의 **남은 모든 턴에서 다시 과금된다**

원래 브리프는 각 에이전트에게 `docs/vocab-corpus-spec.md`(82.5KB) **전문을 Read** 하라고 지시했다.
읽은 내용은 그 에이전트 대화의 일부가 되어 이후 매 추론 턴마다 입력으로 재과금된다.
턴이 10회면 한 지문에서 40k 토큰이 400k 로 불어난다. 실측 지문당 167~207k 와 정확히 맞는다.

**전수 실측(같은 8지문, 4갈래, 각 8기)**

| 갈래 | 브리프 | 지문당 토큰 | 도구 호출/기 | 항목 | 밀도 | critical/major | **항목당 토큰** |
|---|---|---|---|---|---|---|---|
| 대조군 | 원본(스펙 파일 Read) | 170k | 9.9 | 324 | 0.311 | 0 / 0 | 4,202 |
| 컴파일 | 스펙 인라인 | 144k | 6.3 | 327 | 0.314 | 0 / 1 | 3,533 |
| 인라인 | +견본·지문 인라인 | 148k | 7.6 | 352 | 0.338 | 0 / 0 | 3,374 |
| **린** | **+도구 호출 금지 명시** | **125k** | **3.9** | **356** | **0.342** | **0 / 1** | **2,802** |

→ **린 채택.** 항목당 토큰이 대조군 대비 **33% 개선**, 도구 호출은 9.9→3.9.

### 13.2 에이전트는 **시키지 않은 것을 읽는다** — 금지를 명시해야 멈춘다

에이전트 실제 도구 호출을 열어보니 **네 갈래 전부 `scripts/verify-vocab-corpus.ts`(56KB 소스)** 를
읽고 있었다. 게이트 규칙을 알아내려고 구현을 뜯어보는 것이다. 게이트는 위반할 때마다 검사명·§조항·
내용을 출력으로 말해주므로 순수 낭비다. 대조군은 스펙을 **두 번** 읽었고(82KB×2), 인라인 갈래는
`§PASSAGE` 를 줬는데도 `passages.json` 을 다시 읽고 산출 디렉터리에 `ls` 까지 했다.

→ 브리프에 **§1.1 도구 호출 금지 목록**을 두고 "정상 경로는 도구 3회(Write→게이트→반환)"를 못박는다.
   **금지보다 확실한 것은 읽을 이유를 없애는 것**이다 — `§PASSAGE` 에 `meta`(학년·연도·시험·유형)까지
   넣은 뒤로 `passages.json` 재조회가 사라졌다.

### 13.3 배치(에이전트당 여러 지문)는 **역효과**다

고정비(스펙)를 나눠 물릴 수 있으니 이득처럼 보인다. 그러나 비용 동인은 지문 수가 아니라
**턴 × 컨텍스트**다. 한 에이전트가 4지문을 순차 처리하면 턴이 4배가 되고 **앞서 만든 산출물까지
매 턴 재과금**된다. 고정비 절약분보다 누적 컨텍스트 증가가 크다. 그래서 지문 1건 = 에이전트 1기를
유지하고, 대신 **턴 수를 줄인다**.

### 13.4 A/B 는 반드시 **같은 브리프 대조군**과 함께 돌려라

이 라운드에서 대조군이 두 번 판정을 뒤집었다.

1. 컴파일본이 한 파일에서 `over`(~에 걸쳐)·`in fact` 등 §4.1 필수 범주 **9항목을 누락**했다.
   브리프 결함으로 보였다. 그런데 **같은 브리프**로 재추출한 대조군도 기준 대비 누락 36항목·
   겹침 84.9% 로 컴파일본(36항목·85.0%)과 **동일**했다 → 런 간 편차였다.
2. 인라인·린이 밀도를 올렸는데 신규 항목의 51~60% 가 `basic` 이었다. "밀도를 기초어로 채운
   군살"(§4.2 경고)로 보였다. 그런데 대조군도 신규의 **55%가 basic**, `advanced` 는 38→28 로
   같이 줄었다 → 역시 편차다. 린의 `advanced`(29)는 대조군(28)보다 오히려 높다.

→ **편차를 재지 않은 A/B 는 노이즈를 읽는 것이다.** 브리프·모델·프롬프트를 바꿀 때는
   `기준선 / 같은-브리프 대조군 / 변경본` 3갈래를 같은 표본으로 돌려라.

### 13.5 인라인 데이터는 512KB 스크립트 한도를 먹는다

워크플로 스크립트는 **파일 경로로 넘겨도 512KB 상한**이다(실측: 399지문 인라인 = 985KB → 발사 거부).
- `text` 필드는 넣지 마라 — `sentences[].en` 을 이어붙인 것과 같은 중복이다(절반이 준다).
- `meta` 는 추출 판단에 쓰는 것만(grade·year·exam·typeGroup·wordCount).
- 실측 한계: 지문당 약 1.2KB → **트랜치 320건**이 안전선(총 510KB).
- 지문 데이터는 `npx tsx scripts/vocab-pdata.ts --pending --limit=320` 로 **한 프로세스에서** 뽑는다.
  지문마다 `vocab-passage.ts` 를 부르면 프로세스 기동만으로 1,900건에 한 시간이 넘는다.
- ⚠️ `vocab-pdata.ts` 와 `vocab-passage.ts` 는 **반드시 같은 `splitPassageIntoSentences`** 를 쓴다.
  갈리면 에이전트가 받은 `sentences` 와 게이트가 재계산하는 값이 어긋나 불변식 1이 전량 깨진다.
  (검증: 8건 전수로 문장·원문 동일 확인 완료.)

### 13.6 추출 모델 — Sonnet 기각 (2026-07-30 실측)

주간 쿼터가 병목이 되면서 "Sonnet 으로 같은 쿼터에 더 많이 돌린다"를 검증했다.
**브리프·지문·산출 경로를 본선과 완전히 동일하게 두고 `model` 하나만 바꿨다.**

| 갈래 | 항목 | 밀도 | 지문당 토큰 | 항목당 토큰 | idiom | 다의 전치사 |
|---|---|---|---|---|---|---|
| 기준선 | 324 | 0.311 | — | — | — | — |
| 대조군(Opus, 원본 브리프) | 324 | 0.311 | 170k | 4,202 | — | — |
| **린(Opus)** | **356** | **0.342** | **125k** | **2,802** | **26** | 7 |
| 린(Sonnet) | 302 | 0.290 | 141k | 3,724 | 17 | 6 |

**기각 근거 셋:**
1. **원시 토큰이 더 든다.** 지문당 141k vs 125k, 항목당 3,724 vs 2,802 (**33% 악화**).
   쿼터 가중치가 Sonnet 에 유리하더라도 출발점이 불리하다.
2. **밀도가 기준선 밑으로 내려간다.** 0.290 < 기준선 0.311 < 린(Opus) 0.342.
   과소추출은 이 프로젝트가 이미 싸운 1급 결함이다(§4.2.1 참조 밀도 신설 경위).
   편차 대조(기준선 324 ↔ 대조군 324)로 볼 때 302 는 편차 범위 밖이다.
3. **결정적 — 누락이 §4.1 필수 범주에 몰린다.** Opus 가 뽑고 Sonnet 이 놓친 83항목 중 17항목이
   구동사·관용구·전치사·접속사다: `among` · `by` · `over`(다의 전치사) ·
   `as A as possible` · `too A to B` · `not A but rather B` · `not more A than B`(수능 관용 패턴) ·
   `lead to` · `or` · `though` · `where`. **idiom 총량이 26→17(−35%)** 이다.
   기출 단어장의 존재 이유가 이 패턴들인데 그걸 잃는 거래는 성립하지 않는다.

단, 게이트는 깨끗했다(critical 0 · major 0). Sonnet 이 **틀리는** 게 아니라 **덜 뽑는다**.
→ **Opus 로 밀되 쿼터를 며칠에 나눠 태운다.** Sonnet 은 Opus 가 아예 불가할 때의 폴백으로만 남긴다.

### 13.7 린 브리프 대량 검증 — 286건 실측 (2026-07-30)

§13.1 의 채택 근거는 8지문 A/B 였다. 본선 투입 후 **286건**으로 다시 쟀고 결론이 강화됐다.

| 갈래 | 파일 | 밀도 | basic | advanced |
|---|---|---|---|---|
| **린 고3** | 87 | **0.322** | **20%** | **10%** |
| 린 이전 고3 | 600 | 0.290 | 23% | 9% |
| 린 고2 | 88 | 0.316 | 22% | 10% |
| 린 고1 | 111 | 0.307 | 30% | 5% |

**같은 학년끼리(고3 대 고3) 비교하면 린이 양쪽 다 낫다** — 밀도 +11%, basic 은 오히려 낮고
advanced 는 높다. 286건 전체에서 **critical 0 · major 13(전부 TRAP_RATIO, 참고 신호)**.

⚠️ **여기서 배운 것: tier 분포는 학년을 통제하지 않으면 읽을 수 없다.**
린 채택 직후 본선 산출 20건을 보고 "basic 31% / advanced 4% 로 기초어 쏠림"을 의심했는데,
그 20건이 **전부 고1** 이었다(학년 교대 수정 전이었다). 고1 지문은 원래 기초어가 많고 고급어가 적다.
고2·고3 이 흘러들어온 뒤 보니 고3 basic 20% 는 린 이전 23% 보다 **낮았다**.
→ 브리프·모델 비교에서 tier 를 볼 때는 **반드시 같은 학년 대조군**과 맞대라(§13.4 3갈래 원칙의 연장).

### 13.8 §2.6 개정 블라인드 검증 — 신본 3승 0패 2무 (2026-08-01)

§2.6(함정 kind 규율)·§2.7(통합 자기점검)을 넣은 뒤, **그 개정 이전에 뽑힌 지문 5건**을
새 브리프로 다시 뽑아 **판본을 감춘 채** 채점자 5기에게 맡겼다(각 지문 1기, 채점 항목 4개 사전 고정).

블라인드 무결성 — 실제로 새게 했던 구멍 3개를 막고서야 발사했다:
① 브리프에 "한쪽이 최신"을 암시하는 문장이 있었다. ② "두 파일의 `sentences` 가 동일"이라고
썼는데 동일한 것은 `en` 뿐이고 `ko` 는 각자 새로 옮긴 것이라 **문체가 판본 단서**였다.
③ §2.6·§2.7 예시에 블라인드 지문의 **정답이 그대로 들어 있었다**(`for`=~때문에 등).
그리고 해시 배정이 n=5 에서 4:1 로 쏠려 정렬 교대 배정으로 바꿨다.

| 채점 항목 (전부 적을수록 좋음) | 구본 | 신본 | |
|---|---|---|---|
| **kindMismatch** (표제어는 단어 하나인데 note 는 결합형) | 10 | **1** | **−90%** |
| fakeTraps (3단 반증 실패) | 7 | **5** | −29% |
| missedStructural (실재하는 구조·철자 함정 누락) | 21 | 18 | −14% |
| missedMandatory (실재하는 필수 범주 누락) | 11 | 12 | +9% |

**kindMismatch −90% 는 편차가 아니다** — 5지문 중 **4곳이 정확히 2→0** 으로 같은 방향이다.
§2.6-① 이 겨냥한 바로 그 결함이고, 그래서 240건 재추출은 정당하다.

⚠️ **그러나 `missedStructural` 은 거의 안 움직였다(21→18).** 5지문에 **양 판본 합쳐 39건**이다.
§2.6-②·§2.7-4 가 구조 오독을 이미 지시하고 있는데도 안 잡힌다 → **지시가 있는데 안 먹는다.**
진단은 §13.9 에 있다.

### 13.9 왜 구조 함정만 안 잡히나 — 지시의 형태가 다르다 (2026-08-01)

§2.5 의 네 범주는 각각 **판정 절차**를 갖고 있다:
- ① 다의 기능어 → "1순위 뜻으로 **바꿔 읽어보라**. 문장이 달라지면 수록"
- ② 상관 구문 → "**상관어가 보이면** 그 구문 전체가 후보"
- ③ 구동사 → "**예측 가능성 시험**(§3.5)을 통과하면"
- ④ 파생·굴절 → "원형과 **다른 뜻이면**"

반면 구조 오독 점검(§2.7-4)은 **"이 문장에 구조 오독 자리가 실제로 있는가?"** 라는
**예/아니오 질문 + 문법 용어 목록**뿐이다. 절차가 없다.
→ 절차 없는 예/아니오 질문은 기본값이 "아니오"다. 네 범주는 걸리는데 이것만 안 걸리는 이유가 이것이다.

**가설**: 판정을 "함정이 있나?"(판단)에서 **"이것을 짚어라"(위치 지목)** 로 바꾸면 걸린다.
지목은 산출물이 있어서 건너뛸 수 없고, 지목한 뒤에야 3단 반증(§7.2)으로 거르면 된다.

⚠️ 이 가설은 **검증 전까지 라이브 브리프에 넣지 않는다.** 구조 함정을 밀면 가짜 syntax 함정이
느는 것이 정확히 이 프로젝트가 §5.1-c·§7.1·§7.2-b·§12 에서 네 번 겪은 실패 모양이다.
그래서 A/B 의 측정 항목에 **fakeTraps 를 반드시 포함**하고, 늘면 기각한다.
대조군은 **같은 v2 브리프의 새 실행**이어야 한다(§13.4 — 판본 간 편차와 실행 간 편차를 섞지 마라).

넷을 순서대로 지목하게 하고, **"학생이 구체적으로 어디를 잘못 짚는지 한 문장으로 못 쓰면 함정이 아니다"**
라는 브레이크를 같이 걸었다.

**설계**: 지문 5건 × 두 브리프(v2 대조군 / v3) = 코덱스 10회. 같은 모델(luna·high), 같은 지문.
**채점 항목에 `fakeStructural` 을 신설**했다 — "kind 가 syntax/form-confusion 인데 그 자리에 실제
오독 위험이 없고 문법 용어만 댄 것". ④를 줄이려다 ⑤가 늘면 개선이 아니기 때문이다.

3,451건을 다시 뽑을 근거로는 약했다. → **코덱스를 더 쓰지 않고 채점자만 3기로 늘려** 재채점했다.

경합이 심한 창에서 잰 시간 수치는 편차가 신호를 삼킨다(§12.8 과 같은 실수).

### 13.12 세 결함축은 **처방이 서로 다르다** — 모델·사고량·브리프 (2026-08-02 확정)

같은 지문 7건에 네 갈래를 돌려 짝지어 쟀다(본선 러너 정지, 동시 12).

| 갈래 | 항목 | 함정 | 구조계열 | 관용류 | advanced | 소요 |
|---|---|---|---|---|---|---|
| luna·high·현행 | 40.14 | 6.00 | 0.14 | 6.43 | 1.86 | 20.9분 |
| luna·ultra·현행 | 41.29 | 7.86 | 0.86 | 6.57 | 1.86 | 39.2분 |
| **luna·xhigh·광폭** | 39.86 | 5.86 | 0.57 | 6.43 | **3.14** | 24.2분 |
| sol·high·현행 | 41.14 | 7.43 | 0.86 | 8.86 | 2.86 | 26.0분 |

**① `advanced` = 브리프 문제.** effort 를 high→ultra 로 올려도 **1.86 → 1.86, 1도 안 움직였다.**
그런데 브리프에 관점 한 절을 넣으니 **3.14 로 sol(2.86)을 넘었다.** 사고를 더 시켜서 되는 게
아니라 **무엇을 찾는지 시선이 없었던** 것이다.

**② 구조계열 = 사고량 문제.** 0.14 → 0.57(xhigh) → 0.86(ultra) 로 effort 에 정직하다.
브리프를 어떻게 고쳐도(v3 지목 절차·견본 8개·광폭 관점) 이 축은 안 움직였다.

**③ 관용류 = 모델 능력으로 보인다.** 세 갈래 전부 **6.43 · 6.57 · 6.43** 으로 꼼짝 안 했다.
effort 도 브리프도 통하지 않았고 sol(8.86)의 73% 에서 멈춘다.
다단어 덩어리를 하나의 의미 단위로 보는 능력 자체의 차이로 본다.

→ **결함을 만나면 먼저 어느 축인지 가려라.** 셋을 뭉뚱그려 "프롬프트를 고치자"로 가면
  ②③에 브리프를 갈아넣으며 시간을 버린다(2026-08-01 에 그렇게 하루를 버렸다).
  판별법: **effort 만 바꿔 한 번 돌려보라.** 움직이면 ②, 안 움직이면 ①이나 ③이고,
  그다음 브리프를 바꿔 움직이면 ①, 그래도 안 움직이면 ③이다.

### 13.13 브리프는 **좁은 절차보다 넓은 관점**이 먹힌다 (2026-08-02)

`advanced` 를 뚫은 문구는 규칙도 목록도 아니었다. §1.5 로 넣은 **읽는 시선** 한 절이다:

> 고3 학생이 이 지문을 **시험장에서 처음 읽는다**고 상상하라.
> 그 학생이 **읽다가 멈추는 자리**가 이 코퍼스가 담아야 할 전부다. 멈춤은 세 모양으로 온다.
> — **모르는 말**(사전을 찾을 단어) · **아는데 안 맞는 말**(다의) · **낱말은 다 아는데 안 풀리는 말**(덩어리)
> ⚠️ 첫째와 셋째를 놓치기 쉽다. 둘째는 눈에 잘 띄어 그것만 담고 끝내기 쉽다.

**앞선 두 시도는 실패했고, 실패 이유가 같다 — 너무 좁았다.**
- v3(2026-08-01): 문장마다 4단계 지목 절차 + "못 쓰면 함정 아니다" 브레이크
  → 모델이 **브레이크를 빠져나갈 길로 썼다.** 구조계열 0.20 → 0.25.
- 견본판: sol 이 실제로 잡은 구조 함정 8개를 실물로 제시
  → 예시 8종에만 반응하고 그 밖으로 안 퍼졌다.

→ **규칙을 더 쓰지 마라. 무엇을 보는 자리인지 시선을 줘라.**
  좁은 절차는 그 절차만 처리하고 끝나고, 브레이크는 빠져나갈 구멍이 된다.
  넓은 관점은 규칙에 없는 자리까지 걸린다.
  ⚠️ 단, ②처럼 사고량이 병목인 축에는 관점도 안 통한다(§13.12).

### 13.11 ⚠️ **누락 지표는 절대값을 목표로 쓸 수 없다 — 차이로만 써라** (2026-08-01)

3기 반복의 진짜 소득은 승패가 아니라 **편차의 구조**였다. 같은 지문·같은 파일을 세 명이 세면:

| 지표 | 절대값이 흔들리는 폭 | **v3−v2 차이**가 흔들리는 폭 |
|---|---|---|
| missedStructural | **1.4** | **0.2** |
| missedMandatory | 1.2 | 0.4 |
| fakeTraps | 0.6 | 0.4 |

한 지문에서 채점자들이 "구조 자리가 4개 / 5개 / 7개 누락됐다"로 갈렸는데, **어느 쪽이 더 잡았는가**는
셋 다 똑같이 답했다. 즉 채점자마다 "무엇을 함정 자리로 칠 것인가"의 기준선이 다르고,
그 기준선은 **짝지은 비교에서 상쇄된다.**

**따라서:**
- ✅ 두 산출을 **같은 채점자가 나란히** 본 차이 → 신뢰할 수 있다.
- ❌ "missedStructural 을 N 이하로" 같은 **절대 임계값** → 채점자를 바꾸면 값이 바뀐다. 게이트로 쓸 수 없다.
- ❌ 이 수치를 브리프에 목표로 넣는 것 → §12.9 까지 다섯 번 겪은 대리지표 실패의 여섯 번째가 된다.

계측기의 비대칭도 기록해 둔다: `fakeTraps` 는 **존재하는** 함정에 3단 반증시험(§7.2)을 걸지만,
`missedStructural` 은 **없는 자리**에 아무 시험도 안 건다. 그래서 누락 수치는 언제나 **상한**이다.
(양 판본이 공통으로 "놓쳤다"고 집계된 자리 상당수가 실제로 함정으로 성립하는지는 검증되지 않았다.)
