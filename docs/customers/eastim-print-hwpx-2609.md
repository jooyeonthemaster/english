## 1. PDF — 「로딩이 오래 걸려 1~3쪽만 인쇄된다」

### 1.1 재현 (운영과 같은 코드, 고객 시험지 그대로)

인쇄 경로 파일 7개가 **HEAD `cd03143f` 와 바이트 동일**하다. 그래서 HEAD 워크트리를 띄워 고객 세션으로 열었다.
재현 중 POST 요청(인쇄 횟수 증가·추적)은 전부 차단해 **DB 쓰기는 0건**이다.

### 1.2 원인 사슬

1. **지연 마운트(6/29 `02374a2c` 도입)** — `exam-paper-builder-client-parts/preview-pages.tsx` 의 `LazyPaperPage`.
   - 앞 2쪽(`eager={pageIndex < 2}`)만 즉시 그린다. 나머지는 IntersectionObserver가 「화면 근처에 왔다」고 알려야 그린다.
   - 안 그려진 쪽은 `minHeight` 만 가진 빈 틀이다. 인쇄 CSS(`print-styles.tsx`)는 이 틀을 지우지 않는다. 그래서 **빈 틀이 그대로 백지 한 장씩**이 된다.
   - 정답표 쪽은 지연 대상이 아니어서 맨 뒤에 정상 인쇄된다. 이것이 「앞 2쪽 + 백지 + 정답표」 모양의 정체다.
2. **일반 인쇄에는 「전부 그리기」가 없다.** `forceMountAll` 은 「PDF 해설」(`explanationPrint`)에만 걸려 있다(6/30 추가).
   - 아래 버튼은 모두 `handlePrint` → `window.print()` 를 바로 부른다: 「인쇄」, 다운로드 메뉴 「PDF(미리보기 그대로)」, 목록 카드 「인쇄」.
3. **목록 카드 「인쇄」는 더 나쁘다.** `exam-file-card.tsx:304-328` 이 0×0 · `visibility:hidden` iframe에 `/director/exams/{id}?print=1` 을 띄운다. 그러면 페이지가 스스로 print() 한다.
   - 창 크기가 0이라 IntersectionObserver가 **영원히** 발동하지 않는다.
   - 사용자가 스크롤로 구제할 방법도 없다.
4. 상세 화면에서도 스크롤 없이 인쇄하면 1536×730 뷰포트에서 **1·2쪽만** 그려져 있었다.
   - 미리보기가 중첩 스크롤 컨테이너(`#exam-paper-print-root`) 안에 있다. 그래서 IO의 `rootMargin: 1200px` 가 안쪽 컨테이너의 잘림에는 적용되지 않는다.

### 1.3 「로딩이 너무 오래 걸린다」의 실체

- 3쪽 이후는 기다려도 끝내 안 나온다. 고객이 말하는 「로딩」은 사실상 이것이다.
- 여기에 체감 지연이 겹친다(측정치는 §1.6).
  - 카드 「인쇄」를 누르면 **화면에 아무 반응 없이** 숨김 iframe이 상세 페이지 전체를 새로 받는다: 원장 콘솔 레이아웃, 시험지 전 문항, 설정 JSON.
  - 준비가 끝나야 인쇄창이 뜬다. 버튼에 진행 표시가 없다.
- 빌더로 만든 시험지는 `exams.settings` 가 **49만~61만 자**다.
  - 80문항이 지문 4개를 공유하는데, `settings.items[]` 에 문항마다 지문 전문(`passageContent`)을 복사해 둔다. 지문 하나가 20번 중복된다.
  - 인쇄 한 번마다 이 덩어리와 문항 본문·structuredData(80문항 기준 약 20만 자)를 함께 받는다.

### 1.4 9/19 수리의 상태 — 두 겹으로 막혀 있다

`docs/EXAM-PAGINATION-OVERFLOW.md` §4의 「백지 인쇄」 수리(`hooks/use-print-mount-all.ts`)가 이 버그를 겨냥했다. 그러나:

1. **운영에 없다.** 마지막 운영 배포는 9/19 12:49이고, 수리 파일은 9/19 15:14에 생겼다. 커밋·배포 대기 상태로 열흘째다.
2. **그대로 배포해도 안 고쳐진다(가짜 GREEN).** 작업 트리 수리본으로 실측했다.

| 방법 | PDF(80문항, 29쪽) |
|---|---|
| Chrome 자체 인쇄 엔진(printToPDF — beforeprint 실제 발화 확인)으로 스크롤 없이 인쇄 | **내용 있는 쪽 3/29** (수리 전과 같음) |
| 카드 「인쇄」 iframe 경로 | **3/29** |
| beforeprint를 쏘고 **1.5초 기다린 뒤** 인쇄(9/19 검증 스크립트 방식) | 30/30 |

- 이유는 이렇다. 수리 훅은 beforeprint에서 `flushSync(setMountAll(true))` 로 스위치를 동기 반영한다.
- 그런데 `LazyPaperPage` 는 그 스위치를 `useEffect(() => { if (forceMount) setMounted(true) })` 로 받는다.
- 이펙트 안의 setState는 기본 우선순위라 **다음 태스크로 밀린다.** 브라우저는 beforeprint 핸들러가 끝나자마자 인쇄 레이아웃을 뜨므로, 그 사이에 쪽이 그려지지 않는다.
- 9/19 검증(`scripts/exam-pagination/paper-print-check.mjs`)은 beforeprint 뒤 `waitForTimeout(1500)` 을 뒀다. 그 1.5초 동안 비동기 마운트가 끝나서 통과한 것이다.

**→ 구현(26-09-30)**: `use-print-mount-all.ts` 는 **삭제**했다(소유권 판정 없이 모든 beforeprint 에서 전 쪽을 그려, 스튜디오 학습지
인쇄에도 숨은 시험지를 헛마운트했다). `LazyPaperPage` 는 `mounted || forceMount` 를 렌더에서 반영하고, 전 쪽 마운트는
`usePrintPortal` 이 포털을 실제로 탈 때만 한다(Ctrl+P · 메뉴 인쇄의 동기 안전망). 버튼 인쇄는 인쇄 컨트롤러가 준비 완료 신호
(글꼴 · 전 쪽 마운트 · 넘침 가드 · 이미지 · 첫 루트 · 탭 가시성)를 확인한 뒤에만 `print()` 한다. 검증 스크립트의 1.5초 대기는
없앴고 계약 테스트(C7)가 막는다. 설계와 계약: EXAM-PRINT-PIPELINE §3~§5.

### 1.6 체감 시간 실측 (프로덕션 빌드, HEAD)

HEAD를 `next build` → `next start` 로 띄웠다. 목록 카드 「인쇄」를 누른 순간부터 앱이 스스로 print()를 부르기까지를 쟀다(각 3회).

| 시험지 | CPU 1배(이 PC) | CPU 4배 감속(보급형 노트북 근사) | print() 순간 그려진 쪽 |
|---|---|---|---|
| 80문항·29쪽 | 3.0~6.1초 | 8.6~11.5초 | **2 / 29** |
| 107문항·43쪽 | 5.4~13.5초 | 7.6~13.5초 | **2 / 43** |

- 로컬 서버 ↔ 싱가포르 DB 왕복이 끼어 있어 서버 몫은 운영(sin1, DB 옆)보다 과대 측정일 수 있다. 반대로 고객 쪽 전송(한국 → sin1)은 여기 빠져 있다.
- 상세 화면을 직접 열면 첫 쪽이 뜨기까지 11~13초 걸렸다(같은 단서). 전 쪽을 그리려고 끝까지 스크롤하는 데 17~19초가 더 든다(자동 스크롤 기준, 사람은 더 걸린다).
- 정리하면 「로딩이 오래 걸린다」는 **(a) 반응 없는 5~13초 대기 + (b) 기다려도 끝내 안 나오는 3쪽 이후** 두 가지가 겹친 체감이다. (b)가 본질이다.

### 1.7 수정 방향 (26-09-29 제안) → 구현 결과(26-09-30)

| 제안 | 구현 |
|---|---|
| 1. `LazyPaperPage` 렌더 반영 + 수리 훅 유지 | 렌더 반영은 그대로 했다. **훅은 유지하지 않고 삭제** — 전 쪽 마운트는 `usePrintPortal` 한 곳(§1.4 「→ 구현」) |
| 2. 카드 「인쇄」: 보이는 새 탭 또는 「준비 중…」 표시 | 숨김 iframe **폐기** → 같은 문서 안의 보이는 인쇄 대화상자(`exam-print-dialog.tsx`) + 썸네일과 공유하는 데이터 캐시. 모든 인쇄 진입점이 누르는 순간 「준비 중」과 스피너를 그린다(누름 무장, EXAM-PRINT-PIPELINE §3.3) |
| 3. 기다림 없는 실제 엔진으로 검증 | `print-e2e.mjs`(native · button · dialog · deeplink · real-print · force-per-page) + 쓰기 가드. 계약 C7 이 대기를 막는다 |
| 4. 빌더 `passageContent` 중복 저장 → 지문 id 참조 | **하지 않았다**(범위 밖 — EXAM-PAPER-MODEL §13) |

아래는 26-09-29 제안 원문이다.

1. `LazyPaperPage` 가 `forceMount` 를 **렌더에서 바로** 반영하게 한다: `{(mounted || forceMount) ? children() : null}`. 그러면 beforeprint 안의 flushSync 한 번으로 전 쪽이 동기 커밋된다. 수리 훅(`use-print-mount-all`)은 그대로 쓴다.
   - **검증 완료(재현용 워크트리에서만)**: HEAD + 수리 훅 + 위 한 줄. 기다림 없는 실제 인쇄 엔진으로 쟀다.

     | 경로 | 수리 전(운영) | 9/19 수리본 | **제안 수정** |
     |---|---|---|---|
     | 상세 화면 printToPDF 직행(80문항) | 3/29쪽 | 3/29쪽 | **30/30쪽** |
     | 목록 카드 iframe(80문항) | 3/29쪽 | 3/29쪽 | **30/30쪽** |
     | 목록 카드 iframe(107문항) | 3/43쪽 | — | **44/44쪽** |

   - 쪽 수가 1장 늘어난 것은 정상이다. 백지 틀(1075px)이 A4(1123px)보다 짧아 눌려 담기던 것이 사라지고, 본문 29쪽 + 정답표 1쪽이 제대로 나온다.
   - 작업 트리(9/19 미커밋분)에는 빌더(`exam-paper-builder-client.tsx:3073`)와 상세 미리보기(`exam-detail-paper-preview.tsx:660`)에 훅 배선이 이미 있다. 그래서 작업 트리 기준으로 남은 수정은 **`preview-pages.tsx` 한 줄**이다. 검증 스크립트의 1.5초 대기 제거도 함께 한다.
2. 목록 카드 「인쇄」도 같은 beforeprint 경로를 타므로 1번으로 함께 고쳐진다(위 표). 다만 대안을 검토할 만하다.
   - 숨김 iframe을 버리고 상세 화면을 **보이는 새 탭**으로 연다(진행이 눈에 보이고, 인쇄 미리보기 로딩도 사용자가 인지한다).
   - 또는 버튼에 「준비 중…」 표시를 단다.
3. 검증은 반드시 **기다림 없는 실제 인쇄 엔진**(`page.pdf()` 직행, 또는 iframe 경로의 동기 스냅숏)으로 한다. `paper-print-check.mjs` 의 1.5초 대기를 빼야 같은 가짜 GREEN이 다시 안 난다.
4. (별건) 빌더 `settings.items[].passageContent` 중복 저장을 지문 id 참조로 바꾸면, 인쇄·빌더 로딩 양이 절반 가까이 준다. 효과는 크지만 범위가 커서 따로 판단한다.

고객이 받은 107문항 시험지(`cmucvrufq…`, 정답 미포함)를 **운영과 같은 HEAD 코드로 똑같이 생성**했다. 한컴오피스 2024에서 열고 PDF로도 떴다(57쪽). 글자·글꼴 깨짐이나 XML 오류, 마크업 노출은 **없다.** 깨지는 것은 **시험지 구성**이다.

### 2.1 A — 지문이 문항마다 한 번 더 찍히고 정답이 샌다 (107문항 중 54문항)

- 지문이 이미 문항 본문에 들어 있는 유형(빈칸·순서·삽입·어휘·네모 어법·어법·무관·지칭·함축)이 대상이다.
- 이들 문항 **번호 앞에 번호 없는 원문 지문이 통째로** 한 번 더 찍히고, 그 뒤에 문항의 가공 지문이 또 나온다.
- 선생님 눈에는 번호 없는 지문 덩어리가 시험지 곳곳에 끼어 「깨진」 것으로 보인다.
- 더 심각한 것은 **원문이 답을 보여 준다**는 점이다.
  - 17번 빈칸: 빈칸 자리 원문 "an entirely new digital airspace management system" 이 바로 위에 있다(정답 ⑤).
  - 11번 순서: 원문 단락 순서 B→C→A가 정답 ③과 같다.
  - 1번 무관한 문장: 원문에 삽입 문장이 없어 답이 보인다.
- 정답이 노출될 수 있는 문항은 순서·삽입·빈칸·어법·어휘·무관 46문항이다.
- 웹 미리보기와, 고객이 30초 먼저 받은 **DOCX에는 이 중복이 없다. HWPX만** 그렇다.
- **원인**
  - `export-hwpx/route.ts:252-259`: settings NULL 시험지(문제은행 「시험지 만들기」로 만들고 빌더에서 저장 안 한 것)는 문항을 만들 때 `includePassage` 를 넣지 않는다.
  - `_lib/builder-tables.ts:62-71` `resolveGroupPassage` 가 `includePassage !== false` 로 판정한다. 그래서 값이 없으면 「지문 출력」이 되고, 원문을 따로 찍는다.
  - 웹 미리보기는 `paper-item-utils.tsx:323-332` → `passage-policy.ts:183-190` `shouldIncludeSourcePassageByDefault` 로 이런 유형의 기본값을 false로 둔다. HWPX만 그 기본값 정책을 빠뜨렸다.

  - settings NULL 시험지의 HWPX 내보내기 역대 29건(시험지 24개·학원 6곳)이 대상이다.
  - 8/27 이후는 이번 1건뿐이다.
