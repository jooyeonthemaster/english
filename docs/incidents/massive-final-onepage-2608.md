### 4-2. 산술 — 무엇이 확정이고 무엇이 아닌가

`generationMs` 14건: **269,719~269,879ms (평균 269,825, 폭 160ms)**. 270,000에서 175ms 모자란 것은 잡음이 아니라 지문(fingerprint)이다 — 역산하면 요청 시작→생성 시작 오버헤드 **E₀ = 121~281ms**(예산의 0.05~0.10%).

attempt 1의 abort는 `deadlineAt` 정각에 고정되므로, `A`(attempt 0 종료 시각)가 무엇이든 총합은 같다:

```
A ≥ 69.8s  ⇒  총합 = A + (270,000 − E₀ − A) = 269.8s   (A와 무관)
A < 69.8s  ⇒  총합 = A + 200,000 < 269.8s              (관측과 불일치)
```

**✅ 확정: 14건 전부 정확히 2콜이고, 2차 콜은 `270,000 − E₀ − A` 를 받아 데드라인 정각에 잘렸다.**
**❌ 미확정: `A ∈ [69.8s, 200.0s]` 이상은 알 수 없다.** 1차가 자기 상한(200초)에 잘린 것인지, 그 전에 다른 사유로 죽은 것인지 가를 계기(`attempts`)가 **없다**. (현장 확인법: Vercel 로그에서 8/25 `FINAL_ONEPAGE_REPAIR` 를 grep 하면 즉시 갈린다.)

**어느 쪽이든 2차 콜은 승산이 없었다.** 역대 이 경로에서 성공한 가장 빠른 콜이 **107,652ms**(16:44:52 잡: 1차 78.9초 실패 → 2차 107.65초 **성공**)인데, `A = 200s` 면 2차 창은 **69.8초 = 역대 최속 성공 콜의 65%**다. `A > 162.1s` 인 모든 경우 창이 관측된 **모든** 성공 콜보다 짧다.

### 4-3. 진짜 병목 — 캡이 요구분포의 정중앙에 있었다

## 5. 계통 B: 봉투 실패 (8건) — 「완성본이 있어도 버린다」

`generateQuestionText`(`question-generation-llm.ts:1157`)는 `responseFormat==="json_object"` 일 때 AI SDK 의 `output: Output.json()` 을 붙이고 `result.output` 게터로 읽는다. SDK(`ai@6.0.99`):

```js
// ai/dist/index.mjs:4518-4533 — _output 이 채워지는 유일한 조건
if (lastStep.finishReason === "stop") { resolvedOutput = await parseCompleteOutput({text: lastStep.text}) }
// ai/dist/index.mjs:4644-4649
get output() { if (this._output == null) throw new NoOutputGeneratedError(); }   // "No output generated."
```

**조건은 파싱 실패가 아니라 `finishReason !== "stop"` 이다.** MockLanguageModelV3 실측:

| finishReason | result.text | 결과 |
|---|---|---|
| `stop` | `{"a":1}` | 정상 |
| `length` | `{"a":1,"b":` | `No output generated.` |
| `other` | (빈 문자열) | `No output generated.` |
| **`length`** | **`{"a":1}` (완전·유효)** | **`No output generated.` ← 멀쩡한 완성본을 버린다** |

- 파싱 실패였다면 문자열이 달랐다 — `finishReason==="stop"` 인데 JSON 이 깨지면 `NoObjectGeneratedError("No object generated: could not parse the response.")`. **DB에 그 문자열은 0건.**
- `finish_reason` 매핑(`@ai-sdk/openai-compatible:305`): `length`→length, **그 외 전부(`error`·`null`·미지) → `other`**. OpenRouter 는 업스트림이 중도 실패하면 **HTTP 200 + `finish_reason:"error"`** 를 준다.
- 복구 해치(`isRecoverableJsonText`, :1204)는 `error.text` 를 읽는데 `NoOutputGeneratedError` 는 `name/message/cause` 뿐이라 **절대 발동하지 않는다.**

> ⚠ 같은 파일의 형제 함수는 이 함정을 **26-07-03 에 이미 고쳤다**(`:889-892` 주석: *"Output.json() 미사용: output 게터가 파싱 실패 시 throw 해 원문 텍스트에 접근할 수 없게 되고("No output generated", 26-07-03 실측 2유형)…순수 텍스트로 받아 직접 파싱·복구한다"*). **수리가 한쪽에만 적용됐다.**
> 저장소 안 선행 실측도 있다 — `.tmp-final-qa/model-ab-luna-vs-g36.md:41-43`: *"장문에서 gemini 코어가 maxTokens 20000 절단으로 4/4 실패(**No output generated**). 30000으로 올리면 통과. **수정 미적용**"*.

### 5-1. ⚠ 「실패는 오래 걸린다」는 순환논증이었다 — 걷어내면 대비가 역전된다

- 미기록 추정: 46콜 × ≈15~20k 토큰 ≈ **$1.1~1.3**
- ⇒ **이 경로 실원가가 대시보드에서 약 45% 과소 계상.**

대조: resilient 는 `recordCostSafely` 가 게이트 **앞**이라 실패 5건도 전부 원가행이 있다.

> ⚠ 「원가행 0건」을 「모델이 토큰을 안 썼다」의 증거로 쓰면 안 된다. **abort 되면 usage 객체 자체가 안 생기는 구조**일 뿐, 상류는 그 토큰을 생성했고 청구했을 수 있다.

### 8-2. 지문을 지우면 돈 내고 만든 학습지가 경고 없이 물리 삭제된다

- `src/actions/workbench/passages.ts:723 / :749` — `prisma.passage.delete()` / `deleteMany()`, **soft delete 아님**
- `prisma/schema.prisma:791` — `passage Passage @relation(… onDelete: Cascade)`

`PassageReport` 는 `deletedAt` 소프트 삭제를 갖고 있는데 Passage 하드 삭제의 cascade 가 그 보호막을 **완전히 우회**한다. 잡의 `passageId` 컬럼은 `onDelete: SetNull` 로 밀려 **사후 추적선까지 끊긴다.**

실측 피해: 16:32 The Lottery 추출 잡 삭제 시 **성공한 PRIME_FINAL 2건**, 21:4x 빌드업 재추출 시 **성공한 PRIME 10건**이 함께 증발. 성공 잡 30건 대비 살아남은 리포트가 18건인 이유다. **환불도 없다.** (With김쌤도 같은 패턴 11/11.)

## 10. ⚠ 8/26 수리본은 이 조건에서 더 나쁘다

`e1b14f28` 의 새 산술은 1차 콜을 `270 − MIN_CALL_MS(110) ≈ 155~159.8초`로 조인다. 같은 요구분포·같은 상류 속도로 예측하면:

| 1차 창 | 캡(토큰) | 예측 실패율 |
|---|---|---|
| **155s (현 HEAD)** | 17,391 | **80.1%** ← **악화** |
| **200s (8/25 라이브)** | 22,440 | **53.6%** |
| 240s | 26,928 | 28.1% |
| **270s** | 30,294 | **14.0%** |
| 330s | 37,026 | 1.8% |

실측으로도 뒷받침된다 — 8/25 **성공한** 파이널 11건 중 **4건(36%)이 단일 콜로 164.2·165.6·185.5·194.6초**를 썼다. 새 캡에서는 전부 1차에서 잘린다.

그리고 **새 코드는 1차가 자기 상한을 다 쓰면 2차를 아예 안 쏜다** — 가드가 abort 직후에 재는 탓에 남은 시간이 정확히 110,000ms **미만**(2ms 차)이 되어 `break` 한다(`final-onepage.ts:363-370`). **수리 창을 보장하려고 예약한 그 상황에서 예약이 스스로 무효화된다.**

> **1차 조사에서 나왔던 "성공 max 195s vs 벽 270s = 38% 여유 → 데드라인 확대는 처방이 아니다"는 틀렸다.** 실제 절단자는 270,000이 아니라 **별개 상수 `baseTimeoutMs = 200,000`** 이고, 성공 최대 단일콜 194,553ms = **캡의 97.3%(여유 5.4초)**다. 두 상수는 독립이라 270_000 만 늘려도 1차 캡은 1ms도 안 움직인다.
