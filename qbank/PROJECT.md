## 3. 유닛 정의 (원자 단위)

> **1 유닛 = (지문 1개 × 유형 1개)**. 산출 = 그 유형의 변형문항 5~8개 + 각각의 해설.

유닛 단위를 "문항 1개"가 아니라 "유형 1묶음"으로 잡은 이유:
- 같은 지문·같은 유형의 5문항은 **서로 출제 포인트가 겹치면 안 된다**. 한 에이전트가 5개를 동시에 설계해야
  포인트 분산·중복 회피를 보장할 수 있다. 문항별로 쪼개면 5개가 같은 답을 다르게 물어보는 사고가 난다.
- 에이전트 1기당 시스템프롬프트 오버헤드(1.5~2만 토큰)를 5~8문항에 상각한다.

유닛 생애주기:

```
PENDING → AUTHORED → GATED(결정형, 0원) → REVIEWED(적대검수) → REPAIRED → FINAL
                        ↓ blocking                ↓ critical/major        ↑
                        └────────── 재저작 ────────┴──── 수리 ────────────┘
                                        (최대 3회, 초과 시 QUARANTINE)
```

## 4. 파이프라인 (한 유닛)

| 단계 | 실행 주체 | 비용 | 산출 |
|-----|---------|-----|------|
| **P0 지문 무결성** | Opus 5 (지문당 1회, 유형 전체가 공유) | 지문당 1기 | `_passage.json` |
| **P1 저작** | Opus 5 에이전트 (유형 규격 + 품질헌법 + 지문) | 유닛당 1기 | `<SUBTYPE>.md` |
| **P2 결정형 게이트** | **코드** (md-qgen parser/adapter/gate 재사용) | **0원** | `.gate.json` |
| **P3 적대검수** | Opus 5 (저작자와 다른 에이전트, 다중 렌즈) | 유닛당 1기 | `.review.json` |
| **P4 수리** | Opus 5 (검수 지시서 기반, 조건부) | 유닛당 0.3기 | `.md` 갱신 |
| **P5 재게이트+재검증** | 코드 + Opus 5(수정분만) | 0.2기 | `.gate.json` 갱신 |
| **P6 확정 + 메타 부여** | 코드 | 0원 | `.final.jsonl` |

P2 를 **코드로** 돌리는 것이 이 프로젝트의 경제성의 핵심이다. `src/lib/md-qgen` 의 parser/adapter/gate 는
순수 TypeScript 함수이므로 tsx 로 오프라인 호출할 수 있고, 형식 위반·마커 불일치·문장 누락·번호 비연속 같은
기계 판정 가능 결함을 **API 호출 0회로** 전량 걸러낸다. LLM 검수는 기계가 못 보는 것(논리·정답 유일성·미끼
설계·해설 사실성)에만 쓴다.

## 5. 배분 정책 (티어)

사용자 지시: *"최신 자료(2026)는 지문당 200개, 점점 뒤로 갈수록 줄여라. 단 유형당 최소 5개."*

| 티어 | 연도 | 유형당 변형 수 | 지문당 상한 |
|-----|-----|-------------|-----------|
| **S** | 2027, 2026 | 8 | ~208 |
| **A** | 2025, 2024 | 7 | ~182 |
| **B** | 2023~2021 | 6 | ~156 |
| **C** | 2020~2011 | 5 | ~130 |
| **D** | 2010~2003 | 5 | ~130 |

**유형당 5개는 절대 하한이다** (사용자 명시). 지문당 실제 수량은 "적용 가능 유형 수 × 티어 변형 수"이며,
적용 불가 유형(예: 21단어 지문에 글의 순서)은 억지로 만들지 않고 **미적용으로 기록**한다 — 불가능한 조합을
채우려다 억지 문항을 내는 것이 I8 위반이다.

**처리 순서: 최신 연도 우선.** 2027 → 2026 → 2025 → … 가치가 큰 자료부터 완주해 조기 산출을 확보한다.

## 6. 실행 규모와 정직한 산술

- 유닛 수 ≈ 4,537 지문 × 적용가능 유형 ≈ **10만 유닛** (정확값은 `spec/unit-plan.json`)
- 에이전트 호출 ≈ 유닛당 2.3기(저작 1 + 검수 1 + 수리 0.3) ≈ **23만 기**
- 이 머신 동시 실행 상한 = `min(16, 12코어 - 2)` = **10기**
- 에이전트 1기 ≈ 3~5분 → **약 2.5기/분** → 23만 기 ≈ **1,500시간 ≈ 60일 (단일 세션 연속 기준)**

→ **1주일에 끝나지 않는다.** 그러므로:
1. **최신 연도 우선**으로 가치를 앞당긴다 (2027+2026 = 175지문 ≈ 4,000유닛 ≈ 1.5일).
2. **다중 세션 병렬**을 지원한다 — 샤드 클레임 프로토콜(§7)로 N개 세션/계정이 충돌 없이 동시 작업.
3. 진행률은 언제나 `node qbank/harness/ledger.mjs` 로 확인 가능하다.

## 7. 세션 붕괴 내성 (RESILIENCE)

### 7.1 상태의 진실원
워크플로 캐시도, 대화 기억도 아니다. **`qbank/out/` 아래의 실제 파일**이다.
`ledger.mjs` 는 디렉토리를 스캔해 유닛별 상태를 재구성한다. 어떤 세션에서든 즉시 정확한 현황을 얻는다.

### 7.2 새 세션 재개 절차
```
1) qbank/PROJECT.md (이 문서) 읽기
2) qbank/JOURNAL.md 의 마지막 20줄 읽기 — 직전 세션이 무엇을 하다 끊겼는지
3) node qbank/harness/ledger.mjs  → 현황 + 다음 배치 후보 출력
4) 이어서 배치 발사
```

### 7.3 샤드 클레임 (다중 세션 병렬)
`qbank/work/shards/<shardId>.claim.json` 에 `{owner, startedAt, units[]}` 를 기록한다.
- 클레임은 **90분 TTL**. 만료된 클레임은 다른 세션이 회수할 수 있다.
- 유닛 산출은 멱등(I6)이므로 중복 실행되어도 결과가 손상되지 않는다 — 클레임은 낭비 방지용이지 정합성 장치가 아니다.

### 7.4 중단 시 안전성
- 에이전트는 자기 유닛 디렉토리만 쓴다 → 동시 쓰기 충돌 없음.
- 파일이 반쯤 써진 채 죽어도, 다음 스캔에서 `.gate.json` 부재로 `AUTHORED 미완`으로 판정되어 재발사된다.
- 워크플로가 죽으면 `Workflow({scriptPath, resumeFromRunId})` 로 재개하되, **0 순증이면 재개를 멈추고
  인프라 회복을 기다린다** (필살기 규칙).

## 8. 기록 규칙

- **JOURNAL.md 는 append-only.** 관찰마다 `Q###` 번호를 붙인다. 과거 항목을 수정하지 않는다.
- 결론이 뒤집히면 **새 항목으로 추가**하고 옛 항목에 `[폐기→Q###]` 태그만 단다.
- "확정"이라는 단어는 `STATE.md` 에서만 쓴다.
- 이 규칙은 선행 캠페인(`experiments/question-quality-20260715/research-ledger.md` §0)에서
  "매번 최종 확정 선언 후 말없이 뒤집혀 추적 불가" 사고를 겪고 세운 재발 방지책이다. 그대로 계승한다.
