## 1. 불변조건 — 어떤 상황에서도 깨지 않는다

`qbank/PROJECT.md` §1 이 정본이다. 요약:

| # | 불변조건 |
|---|---|
| I1 | **과금 외부 API 호출 0건.** 구독 기반 에이전트로만 작업한다. |
| I2 | 산출물은 `src/lib/md-qgen` 파이프라인과 **바이트 호환**인 마크다운. 자체 포맷 발명 금지. |
| I3 | 지문에 오류가 있으면 **그 지문의 전 유닛을 격리**한다. |
| I4 | **검수자 ≠ 저작 모델.** (⚠ 아래 경고 참조) |
| I5 | **상태의 진실원은 파일시스템.** 대화 기억·캐시가 아니라 `qbank/out/` 의 실제 파일. |
| I6 | **멱등 소유권.** 한 유닛 = 한 디렉토리, **전면 교체**. 부분 수정 지시 금지. |
| I7 | 게이트가 "0건"을 보고하면 **결함을 주입해 검출력을 증명**한 뒤에만 신뢰한다. |
| I8 | **양이 품질을 대체하지 않는다.** 미달은 미달로 기록하고 넘어간다. |

### ⚠ I4 는 단독 운영에서 부분적으로 깨진다 — 반드시 읽어라

I4 는 실측으로 세워진 조항이다. 같은 3유닛에서 **Claude 검수 critical 1건 vs Codex 검수 12건**,
그리고 **블라인드 풀이 불일치 3건**이 나왔다. 이유는 노력 차이가 아니라 **구조**다 —
저작자와 같은 모델은 같은 사고 경로로 풀어 같은 정답에 도달하므로,
*"다른 경로로도 풀리는가"* 를 물을 수단 자체가 없다. 정답 복수 성립(V2)이 그대로 통과한다.

**네가 단독으로 저작·검수를 다 하면 이 검사가 사라진다.** 숨기지 말고 인지하라.

**대체 수단 (완전하지는 않다)**:

1. **반증 단계는 동일 모델에서도 작동한다.** 실측 근거가 있다 — 검수 critical 16건 중
   **10건이 같은 모델의 반증자에게 기각**됐고, 그 반증은 코드 줄을 인용하며 엄밀했다.
   즉 *역할을 반대로 지정하면* 동일 모델에서도 유의미한 교차가 생긴다. **반증 단계를 절대 빼지 마라.**
2. **결정론적 게이트에 더 의존하라.** 게이트는 모델이 아니라 코드다(§4). 사람·모델의 합의와 무관하게 참이다.
3. **블라인드 풀이는 형식적으로라도 유지하라** — 정답·해설을 실제로 가리고 풀어라.
   같은 모델이라 효과가 줄지만 0은 아니다.
4. **주기적으로 Claude Code 를 한 번씩 태워라.** 발주자가 Claude Code 를 실행할 수 있다.
   지문 20~30개마다 한 번 교차검수를 돌리는 것만으로도 계통 결함을 잡는다.
   교차검수 워크플로는 이미 만들어져 있다: `qbank/harness/wf-crossreview.js`.

## 4. 하네스 — 명령 사전

### 4.1 게이트 (가장 중요) — 0원, 프로덕션 파이프라인을 그대로 호출한다

```bash
node qbank/harness/.build/gate.mjs --passage <passageId> --type <SUBTYPE>
node qbank/harness/.build/gate.mjs --all           # 전수
```

**이것이 이 프로젝트의 심장이다.** `src/lib/md-qgen` 의 파서 → 어댑터 → 게이트를
순수 TS 함수로 호출한다. API 호출 0건이므로 **몇 번을 돌려도 공짜다.**
저작할 때 **PASS 날 때까지 반복하라.**

⚠ `.build/gate.mjs` 는 **빌드 산출물**이다. `qgen-core.ts` 나 `src/lib/md-qgen/*` 를 고치면
반드시 다시 빌드하라 (`codex-pool.mjs` 는 시작할 때 자동으로 한다):
```bash
./node_modules/.bin/esbuild qbank/harness/gate.ts --bundle --platform=node --format=esm \
  --target=node20 --outfile=qbank/harness/.build/gate.mjs --external:node:* --log-level=warning
```
**왜 번들인가**: `tsx` 로 부르면 호출마다 전체를 재컴파일한다. 동시 15기가 그러면
CPU 가 포화되어 **게이트 1회가 66초**까지 늘어난다(실측). 번들은 같은 부하에서 13초다.

### 4.2 저작·검수·수리 워커풀

```bash
node qbank/harness/codex-pool.mjs --batch <배치파일> --role author  --concurrency 10
node qbank/harness/codex-pool.mjs --batch <배치파일> --role review  --concurrency 10
node qbank/harness/codex-pool.mjs --batch <배치파일> --role repair  --concurrency 10 --any-status
```
- `--role` 별 처리 대상 상태가 다르다(`author`=PENDING/GATE_FAILED/AUTHORED, `review`=GATED 이상, `repair`=REVIEW_ISSUES).
- `--effort` **를 주지 마라.** 안 주면 `~/.codex/config.toml` 의 `model_reasoning_effort = "ultra"` 가 그대로 적용된다.
  (과거에 shim 이 `high` 를 무조건 넘겨 사용자 설정을 조용히 하향시킨 사고가 있었다.)
- 로그: `qbank/logs/codex/<passageId>__<SUBTYPE>__<role>.log`

### 4.3 배치 생성

```bash
node qbank/harness/batch.mjs --year 2027 --limit 120 --out qbank/work/prod-2027-003.json
```
⚠ 생성된 배치에는 **이미 완료된 유닛도 섞여 있다.** 상태가 `PENDING` 인 것만 남기고,
**진행 중인 다른 배치와 겹치지 않게** 걸러라. 겹치면 두 워커가 같은 파일을 쓴다.

### 4.4 지문 무결성 감사

```bash
node qbank/harness/codex-audit.mjs --year 2026 --limit 74 --concurrency 10
```
`qbank/out/<year>/<id>/_passage.json` 을 만든다. 이미 있으면 건너뛴다(중단내성).

### 4.5 상태 확인

```bash
node qbank/harness/status.mjs --year 2027     # 유닛별 PASS/FAIL 한눈에
node qbank/harness/ledger.mjs                 # 연도별 진행률
node qbank/harness/slots.mjs                  # 현재 전역 슬롯 사용량
node qbank/harness/measure-options.mjs        # 선지 길이 계량
node qbank/harness/collision.ts               # 문항 간 정답 누출 분석(tsx 필요)
```

### 4.6 전역 동시성 — 반드시 지켜라

`codex-pool.mjs` 와 `codex-audit.mjs` 는 `slots.mjs` 의 **전역 상한**을 공유한다
(코어 수 × 1.5, 12코어 → 18). 여러 풀을 동시에 띄워도 합계가 상한을 넘지 않는다.

**직접 `codex exec` 를 대량으로 띄우지 마라.** 그러면 governor 를 우회한다.
과거에 풀 4개를 각자 상한 지켜 띄웠다가 합계 39가 되어 **CPU 100% · 여유메모리 1.8GB**로
기계가 스래싱했고, `tasklist` 한 번이 120초를 넘겼다.

## 5. 표준 작업 순서 — 지문 하나를 완주시키는 법

```
① 지문 감사        codex-audit.mjs   → _passage.json (ok:true 여야 진행)
② 배치 생성        batch.mjs         → work/*.json  (PENDING 만, 중복 제거)
③ 저작            codex-pool --role author   → <SUBTYPE>.md + .gate.json
④ 게이트 확인      status.mjs        → blocking 0 확인
⑤ 검수            codex-pool --role review   → <SUBTYPE>.review.json
⑥ 반증            ★ 절대 빼지 마라 (§6-A)
⑦ 수리            codex-pool --role repair
⑧ 재검수          ⑤ 반복 → 등급 개선 확인
⑨ 충돌 분석        collision.ts      → 같은 지문의 문항 간 정답 누출 검사
```

**⑥을 빼면 안 되는 이유는 §6-A 에 실측 근거와 함께 있다.**

   감사와 저작을 병행하되, 저작 대상은 반드시 `_passage.json` 이 `ok:true` 인 지문으로 한정하라.

## 6. ★ 함정 원장 — 여기서 피 흘렸다. 같은 데서 또 흘리지 마라

### A. 검수 결과를 그대로 믿지 마라 — 63%가 오탐이었다

교차검수 18유닛에서 critical **16건 중 10건이 반증에서 기각**됐다. 기각 사유 4종:

1. **형식 계약을 결함으로 오인**(최다). 검수자가 "변형 단락이 연결사를 바꿔 게이트를 우회했다"고
   지적했는데, `gate-order-variant.ts:295-308` 은 정반대로 **단서를 지우면 반려**하고
   `ORDER_CUE_KINDS(:74,77)` 가 그 대체 표현을 **승인 어휘로 열거**하고 있었다.
   → **구조를 지적하기 전에 그 유형의 게이트 소스를 열어 금지인지 강제인지 확인하라.**
2. **정량 주장 미검산.** "오답 4개 중 3개 즉사" → 재계산하니 최대 2/4.
   정답 선지도 같은 표면 특징을 가져서 그 휴리스틱은 아무것도 소거하지 못했다.
   → **배제 휴리스틱을 주장하려면 5개 선지 전부에 실제로 적용해 보라.**
3. **구판본 검수**(2건). 저작 풀이 도는 중에 검수를 걸어서 생겼다.
   → **저작이 끝난 뒤에 검수하라.** 인용할 문자열이 지금 파일에 실재하는지 확인하라.
4. **심각도 부풀리기.** critical 은 "출제하면 안 된다"는 뜻이다. 개선 여지는 major 이하다.

**그리고 등급을 raw finding 으로 매기면 오진한다** — 보고된 `F 5개`가 확정 기준으로는 **0개**였다.
반드시 **반증 통과분으로만** 등급을 재산정하라.

### B. 미검증 지적으로 규범을 고치지 마라

위 오탐을 모르고 raw finding 으로 저작 지침을 개정했다가 되돌렸다(JOURNAL Q065).
**적대적 검수의 산출은 결론이 아니라 가설이다.** 반증 통과 전에 규범을 고치면
잘못된 규범이 팬아웃으로 증폭된다.

### C. 게이트가 "0건"이라고 초록이 아니다 (I7)

게이트를 만들거나 고치면 **일부러 결함을 주입해 잡히는지 확인**하고 되돌려라.
예: `few-key-points` 필터를 넣은 뒤 KILLER 해설을 80자 미만으로 잘라 넣어
`thin-killer-explanation` 이 **그 문항에** 뜨는지 확인했다.

### D. 계기가 거짓 경보를 울릴 수도 있다

"정답이 최장 선지" 위반 3건(2.0%)을 보고 게이트를 만들려 했다. 그런데
**우연 기준선과 대조하니 기대 13.7건 vs 관측 3건 = 우연의 0.22배**였다 — 이미 잘 지켜지고 있었다.
이어서 과잉교정을 의심해 χ² 를 쟀더니 81.42("편향 있음")가 나왔는데, **그 통계가 무효였다** —
선지 길이 편차 중앙값이 1이라 대부분 동점이고 동점 평균순위가 전부 3으로 몰린 인공물이었다.
동점에 견디는 척도(정답 길이 − 오답 평균)로 바꾸니 **t=−0.75, 단서 없음**.

→ **경보를 믿기 전에 계기의 가정을 확인하라. 위반 절대수가 아니라 우연 기준선과 비교하라.**
→ **단측 금지 규칙을 게이트로 만들면 반대편 편향을 제조한다.** 양측 척도로 검증하라.

### E. 저자가 고칠 수 없는 경고를 보여주면 무한루프가 된다

`QUALITY:few-key-points` 가 매 시도마다 같은 문항에 다시 떠서 재저작이 반복됐다
(attempts 평균 3.29). 원인은 **md 어댑터 24개 전부가 `keyPoints: []` 를 의도적으로 낸다**는 것
(정본 `adapter.ts:319-322`, 26-07-21 실사고 — 합성 keyPoints 가 모델 오태깅을 학생 표면에 노출).
프로덕션은 md 레인에서 품질 이슈를 **차단하지 않으므로** 무해했지만, 우리는 저자에게 되먹인다.
→ `qgen-core.ts` 의 `STRUCTURALLY_UNSATISFIABLE` 집합으로 걸렀고 attempts 가 **1.75로 감소**했다.
→ 이 집합에 코드를 추가하려면 **"저자가 어떻게 고쳐도 사라지지 않는다"를 증명**하라.
   자주 뜬다는 이유로 넣으면 그것은 게이트 무력화다.

### F. 유형 표면을 이름에서 추론하면 틀린다

`ANTONYM` 은 단어를 바꾸지 않고 **표시만** 한다. `WORD_ORDER` 는 순서를 숨기지 않는다(PASSTHROUGH).
`SENTENCE_ORDER` 의 정체성은 `givenSentence` 가 아니라 **절단 좌표**다
(이걸 몰라서 문항 수가 2개로 잘못 상한선을 만들었고, 고치니 8개가 나왔다).
→ **유형 규격(`spec/types/*.md`)과 어댑터 소스를 직접 읽어라.**

### G. 지문 격리와 교정을 구분하라

`ok:false` 는 그 지문의 유닛 26개를 통째로 폐기한다. 철자 오타 하나로 그러면 코퍼스가 반토막 난다.
판단 기준은 하나다 — **"원문이 무엇이었는지 확정할 수 있는가?"**
확정 가능(고유명사 철자·오타) → `flag` + `suggestedFix`, **사용 가능**.
확정 불가(복원 실패·논리 파손·절단) → `block`, 격리.

### H. 남의 설정 파일을 덮어쓰지 마라

shim 이 `model_reasoning_effort="high"` 를 무조건 넘겨 사용자의 `ultra` 설정을 조용히 하향시켰다.
**"합리적 기본값"을 넣는 것이 곧 설정 무력화다.** 명시 요청이 있을 때만 덮어써라.

### I. 문항 수는 표적 수가 아니라 **서로 다른 정답의 수**로 센다

게이트에 `ANSWER_DUPLICATE` 가 있다. 표적이 8개 있어도 정답이 겹치면 반려된다.
저작 전에 **서로 다른 정답이 몇 개 나오는지** 세라. 못 채우면 `shortfallReason` 에 선언하라 —
**품질을 낮춰 개수를 채우는 것은 I8 위반이다.**

### J. 잡다한 운영 사고

- `codex exec` 의 플래그는 **하위 명령 뒤**에 온다. `codex --skip-git-repo-check exec` 는 죽는다.
- `stdin` 을 `/dev/null` 로 닫아라. 안 하면 영원히 멈춘다.
- 맨 숫자로 로그를 grep 하지 마라 — `429` 를 찾았더니 전부 `parser-content-match.ts:429` 같은
  **줄 번호**였다(속도 제한은 실제로 0건이었다). 반드시 문맥을 확인하라.
- Windows 에서 `import.meta.url` 전문 비교는 드라이브 문자 대소문자 때문에 안 맞는다.

## 7. 저널 규약 — 반드시 지켜라

발주자 지시: *"무조건 작업하다가 세션이 끊기고 난리날거야. 반드시 모든 과정들을 철저하게 기록하고,
진짜 작업 일지를 철저하게 관리하면서 진행하도록 해."*

`qbank/JOURNAL.md` 에 **작업 단위마다 append** 하라. 형식:

```markdown
### Q0NN · <한 줄 제목>
<무엇을 했는가 — 명령과 숫자>
<무엇을 발견했는가 — 실측값. "개선됐다" 말고 "3.29 → 1.75">
<왜 그렇게 판단했는가 — 근거 파일·줄 번호>
**교훈**: <다음 사람이 같은 실수를 피할 수 있게>
```

**규칙**:
- **실패도 기록하라.** Q065 는 내가 틀린 기록이고, 그게 이 저널에서 가장 값진 항목 중 하나다.
- **숫자를 써라.** "좋아졌다"는 기록이 아니다.
- 결론이 바뀌면 **이전 항목을 지우지 말고 새 항목으로 정정**하라. 왜 바뀌었는지가 자산이다.
- `qbank/STATE.md` 는 현재 상태 요약이므로 **덮어쓰기**로 갱신한다.

## 9. 성능 참고 (실측)

| 지표 | 값 |
|---|---|
| 유닛당 저작 시간 | 약 2,600초 (동시 15, `attempts` 평균 1.75) |
| 게이트 1회 | 번들 13초 (부하 시) / `tsx` 66초 — **반드시 번들 사용** |
| 지문 감사 1건 | 약 1,000초 |
| 전역 동시 상한 | 18 (12코어 기준, `slots.mjs` 가 자동 계산) |

동시 15 기준 시간당 약 20유닛. 109,703유닛이면 산술적으로 **약 224일**이다.
발주자는 *"60일 걸려도 상관 없어. 그냥 우직하게 진행해"* 라고 했으나 224일은 그보다 길다.
**처리량을 더 올리려면**: 게이트 번들이 이미 적용됐으니 다음 레버는 `attempts` 를 1에 가깝게
줄이는 것이다(= 첫 시도에 게이트를 통과하는 저작). 실패 원인을 로그에서 집계해
지침을 고치는 것이 동시성을 올리는 것보다 싸다.
