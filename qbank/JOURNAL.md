### Q011 · ★ [정정→Q010] 프로덕션 프롬프트는 "형식 계약"만 계승하고 "저작 지침"은 전면 재설계한다

- stdfix 라운드: 빈칸 contract 유형필터로 **-16.5KB/콜** 다이어트 (원가 압박이 설계를 깎았다)
- O209 심플스택: 빈칸 21.6s/14원 — **검수 없음, 0원 게이트만**. 속도·원가가 1차 목표인 물건이다.

Opus 5 에는 그 제약이 하나도 없다. 프로덕션 프롬프트를 그대로 쓰면 **모델을 flash 천장에 묶는 것**이다.

**확정 — 계약 2층 분리:**
| 층 | 정의 | 처분 | 진실원 |
|---|---|---|---|
| **형식 계약(FORMAT)** | parser/gate 가 기계적으로 강제하는 마크다운 문법 — 라벨축·`정답:`·`해설:`·`오답:`·마커 표기·선지 수 | **불변, 프로덕션 계승** | `parser-*.ts` / `gate-*.ts` |
| **저작 지침(CRAFT)** | 무엇이 좋은 문제인가 — 출제 포인트 선정·미끼 기제 설계·난이도 조성·해설 논리 | **전면 재설계** | 신규 `qbank/spec/craft/<SUBTYPE>.md` |

형식 계약을 어기면 웹·시험지·워드/한컴이 깨진다(불변조건 I2) → 절대 손대지 않는다.
저작 지침은 품질의 전부다 → Opus 5 상한 기준으로 새로 쓴다. **사용자가 전 유형 프롬프트 수정을 명시 승인함.**

**증명 절차(사용자 지시)**: 같은 지문 × 같은 유형에 대해
`A안 = 프로덕션 프롬프트 + Opus 5` vs `B안 = 심층 저작 지침 + Opus 5` 를 저작하고,
① 0원 게이트(형식 준수율) ② 블라인드 심판(공예 점수) 로 **실측 비교**한 뒤 승자를 전 유형에 일반화한다.
프롬프트를 실측 없이 갈아치우지 않는다 — 선행 캠페인의 "10개 표본 승자 일반화" 기각 사유를 반복하지 않기 위함.

**정찰이 확정한 결정적 사실 (전문은 `spec/recon/00-contract.md`)**:
1. **1 마크다운 = 정확히 1문항.** 파서는 첫 매치만 취한다(`parser.ts:83,122,153`) → 한 파일에 5문항을 붙이면
   2~5번이 조용히 사라진다. **내 `<!-- ITEM n -->` 컨테이너 설계가 옳았음이 확인됐다** — 하네스가 1문항씩 잘라 넣는다.
2. **장식은 관용이지 계약이 아니다.** `decoration.ts` 를 import 하는 파일은 10개뿐이고 **정본 `parser.ts` 는 미포함**
   → 빈칸·어법에 `**정답:**` 를 쓰면 정답이 통째로 사라지고 게이트가 「정답 누락」이라는 **거짓 원인**을 지목한다.
   `parser-title.ts` 는 또 자체 정규식이라 표 파이프를 흡수하지 않는다. **저작 규칙 = 장식 0.**
3. **서술형 계열은 `정답:` 줄이 없다** — 조건부영작·문장변형·어순배열은 `모범답안:`, 요약문영작·주제문쓰기는
   `정답(A):` 계열. **26유형 일괄 템플릿에 `정답:` 을 박으면 이 유형들이 전량 반려된다.**
4. **마커 밖 지문 1글자 변경 = 즉사.** 재구성 대조 게이트가 마커를 되돌려 원문과 `normalizeWs` 비교
   (`parser.ts:288-302`). 흡수되는 차이는 곱슬따옴표·en/em dash·`…` 뿐.
5. **게이트 판정의 진실원은 `parsed.gateIssues` 하나.** `validateQuestionQuality` 는 프로덕션에서 **비차단·기록만**

   웹 통과율과 하네스 통과율을 환산하지 않기 위함. 재저작(retry)도 하네스엔 없다.

유일최장 보유 문항에서 **기대 13.7건 vs 관측 3건 = 우연의 0.22배**.

**3차 — 과잉교정 의심**: 단측 규칙("최장이면 안 된다")은 반대 단서(정답=최단)를 만든다.
정답의 길이 순위 분포를 χ² 로 쟀더니 **81.42 (임계 9.49) — "편향 있음"**.
→ **그러나 이 통계는 무효다.** 편차 중앙값이 1이라 선지 대부분이 동점이고,
동점 평균순위가 전부 3으로 몰린 **인공물**이었다. 균등 순위 가정이 동점 데이터에서 깨진다.

**4차 — 계기 교체**: 동점에 견디는 척도는 `정답 길이 − 오답 평균 길이` 다.
**n=146, 평균 −0.05어절, 표준편차 0.81, t=−0.75 → 0과 구분 안 됨.**
저자별로도 Codex t=0.18 · Claude t=−1.24 로 둘 다 정상.

**결론: 게이트 추가하지 않는다.** 길이 단서는 존재하지 않고, 단측 게이트를 넣었다면
저자를 정답 축소 방향으로 몰아 **반대 단서를 제조**할 뻔했다. 교리 산문 + 검수 렌즈로 충분하다.

**교훈 3건**:
1. **게이트를 만들기 전에 그 규칙이 이미 지켜지고 있는지부터 재라.** 위반 건수(3건)만 보면
   커 보이지만 **우연 기준선과 비교**해야 의미가 나온다. 절대수는 판단 근거가 아니다.
2. **단측 규칙을 게이트로 만들면 반대편 편향을 제조한다.** 금지 규칙은 양측 척도로 검증하라.
3. **χ² "편향 있음"을 그대로 보고할 뻔했다.** 동점이 많은 데이터에 순위 통계를 쓰면 중앙으로
   몰리는 인공물이 나온다. 계기가 경보를 울리면 **경보를 믿기 전에 계기의 가정을 확인**하라 —
   이번엔 계기가 "0건"이 아니라 **거짓 경보** 쪽으로 거짓말했다(음성테스트의 반대 방향).

**실재하는 결함 1건**: `q23/SENTENCE_ORDER` 가 2문항(하한 8) 으로 blocking.
문항 자체는 절단 좌표를 S1 / S1-S2 로 분화한 우수한 산출이고, **8문항이 불가능해서가 아니라
내가 고친 `ANSWER_DUPLICATE` 오탐 때문에 2개에서 멈춘 것**이다(절단점 1개 기준만 분할 15가지).
→ 재저작 발사(`fix-q23-sentence-order.json`).

**병행 작업 상태**: Codex 저작 60유닛 5기 동시 가동 중(q20 4유닛 착지, 전부 PASS) ·
Claude 수리 워크플로 128기 중 69기 완료(54%, 오류 0).

### Q060 · 재시도 2~3배의 근본원인 — 저자가 고칠 수 없는 경고 1개
Codex 첫 완주 실측: `TITLE 962s attempts=2` · `TOPIC 1640s attempts=3`.
동시 5 기준 시간당 13.8유닛 → **전체 109,791유닛에 331일**. 60일 목표를 크게 넘는다.
동시성보다 **재시도가 더 싼 레버**라 원인부터 팠다.

**단일 원인이었다.** 세 유닛 로그 전부에서 반복 등장한 품질 이슈는 `QUALITY:few-key-points`
하나뿐이고, **매 시도마다 같은 문항 번호에 같은 코드**가 다시 떴다(TITLE 5·6 / TOPIC 5·6 / MAIN_IDEA 2·3·6).
저자가 재저작해도 사라지지 않는다는 뜻이다.

**왜 사라지지 않는가**: `validateKillerBar`(`question-quality/validators/misc.ts:78-81`)가
KILLER 에 `keyPoints.length >= 3` 을 요구하는데, **md 어댑터 24개 전부가 `keyPoints: []` 를 낸다.**
채우는 어댑터는 0개다. 근거는 정본 `adapter.ts:319-322` 의 26-07-21 실사고 —
합성 keyPoints 가 모델의 포인트코드 오태깅(전치사 Despite 에 형용사 형부)을 **학생 표면까지 노출**시켰다.
정본은 "빈 배열 = 검증기 스킵"을 의도했지만 검증기가 빈 배열도 위반으로 세어 경고가 남았다.

**프로덕션은 왜 멀쩡했나**: `adapter-conditional-writing.ts:19-21` 에 그대로 적혀 있다 —
*"KILLER 에서 few-key-points 경고가 뜨지만 warning 이라 무해하고, md 레인은 품질 이슈를 차단하지 않는다."*
프로덕션은 이 이슈를 **저자에게 되먹이지 않는다**. 우리는 기준을 올려 되먹였고,
그래서 만족 불가능한 경고가 재저작 루프를 돌렸다.

**조치**: `qgen-core.ts` 에 `STRUCTURALLY_UNSATISFIABLE` 집합 신설, `few-key-points` 등재.
음성테스트로 검출력 확인 — KILLER 해설을 80자 미만으로 잘라 주입하니
**주입한 그 문항(#5)에 `thin-killer-explanation` 이 정확히 떴고**, `few-key-points` 만 사라졌다.
집합에 코드를 추가하려면 *"저자가 어떻게 고쳐도 사라지지 않는다"* 를 증명해야 한다고 주석에 못 박았다 —
자주 뜬다는 이유로 넣으면 그것은 게이트 무력화다.

**교훈**: **품질 이슈를 저자에게 되먹이는 순간, 만족 불가능한 이슈는 무해한 경고가 아니라 무한루프가 된다.**
프로덕션이 "warning 이라 무해"라고 적어둔 것은 프로덕션의 사용 방식에서만 참이다.
남의 검증기를 다른 용도로 재사용할 때는 **그 검증기의 전제(fast 레인 계약)가 우리 레인에서도
성립하는지**를 코드별로 확인해야 한다.

### Q063 · 풀마다 동시성을 정했더니 합계가 기계를 죽였다 — 전역 governor 신설
저작 1차(5) + 저작 2차(15) + 수리(8) + 순서수정(1) + 감사(10) 을 각각 띄웠다.
각 풀은 **자기 상한을 정확히 지켰다.** 그런데 합계가 39 였다.

실측 결과: **codex 79 프로세스 · node 192 · CPU 100% · 여유메모리 1.8GB.**
`tasklist` 한 번이 120초를 넘겨 타임아웃했다. node 192 개의 정체는 에이전트들이
자가 게이트 루프에서 부른 `tsx` 다(게이트 번들화 Q061 이 그 축을 5배 줄이지만,
이미 도는 에이전트는 구 프롬프트를 쓴다).

**아무도 합계를 보지 않았다는 것이 결함이다.** 풀의 `--concurrency` 는 자기 상한일 뿐
기계 전체의 예산이 아니다. → `slots.mjs` 신설: 모든 러너가 작업 하나를 시작하기 전에
전역 슬롯을 잡고, 상한을 넘으면 대기한다. 상한은 **코어 수에서 유도**한다(`cores × 1.5`,
12코어 → 18) — 숫자를 손으로 박으면 다른 기계에서 다시 터진다.

**계기가 가장 필요한 순간에 고장 났다.** 1차 구현은 `tasklist` 로 codex 프로세스를 셌는데,
부하가 높을 때 정확히 타임아웃했다(실측 `running:-1` → fail-open 으로 통과 = governor 무용지물).
부하와 무관하게 동작해야 하므로 **파일 기반 카운터**로 교체했다 —
`qbank/.slots/` 의 엔트리 수를 세고, 하트비트(30초)로 갱신하며 90초 넘게 갱신이 없으면
죽은 워커의 락으로 보고 회수한다. 디렉토리 읽기는 CPU 포화와 무관하게 빠르다.

**음성테스트**: `QBANK_SLOT_CAP=2` 로 2개를 잡은 뒤 3번째를 요청하니 **10초 대기 후 획득**했다
(6초 시점에 1개 해제). 상한이 실제로 막는 것을 확인한 뒤에만 신뢰한다(I7).

**규범 충돌 1건 제거**: 감사 프롬프트가 앞에서는 "확신 없으면 `ok:false`",
뒤에서는 "`ok:false` 는 block 일 때만" 이라고 말하고 있었다(Q062 개정의 부작용).
감사관이 어느 쪽을 따를지 알 수 없다 — 앞 조항을 "판단이 안 서면 `confidence:low` +
issues 에 기록, 심각도는 격리/교정 규칙으로 결정"으로 고쳤다.

**교훈**: **자원은 작업 단위가 아니라 기계 단위로 예산을 짜라.** 각자가 규칙을 지켜도
합계가 한도를 넘으면 전부 느려진다. 그리고 **부하를 재는 계기는 부하에 강건해야 한다** —
부하가 높을 때 죽는 계기는 없는 것보다 나쁘다(있다고 믿게 만드니까).

### Q064 · 교차검수 18유닛 완주 — V3(미끼)가 지배 원인, 근본원인 1개로 수렴

실제 최댓값과 일치하는지 확인 — 실측에서 저자가 지목한 최강 미끼가 실제 최강과 **달랐다**.
선언이 자기 설계와 어긋나면 설계를 안 한 것이다.

**계측 정의 결함 1건 발견(미해결)**: 블라인드 불일치 4건이 전부 `SUMMARY_COMPLETE`·
`CONDITIONAL_WRITING` — **서술형**이다. 서술형에서 검수자가 "다른 문장"을 쓰는 것은
정답 붕괴가 아니라 정상이다(채점 기준으로 맞는지가 관건이지 문자열 일치가 아니다).
`matchesIntended` 를 객관식과 서술형에 같은 뜻으로 쓰는 지금 스키마는 **서술형에서 오탐을 만든다.**

### Q065 · ★ 내가 미검증 지적으로 교리를 고쳤다 — 반증이 16건 중 10건을 기각
Q064 에서 "V3 즉사가 critical 16건 중 7건 = 최다"라며 지침에 **P1-b** 와 자기반증 11번을 신설했다.
**그 근거가 반증 단계에서 무너졌다.** 워크플로가 완주하자 `criticals: {raw:16, confirmed:6, refuted:10}` —
**63%가 기각**됐고, 내가 인용한 V3 즉사 건들은 거의 전부 기각 쪽이었다.

**나는 반증 단계가 아직 도는 중에 raw findings 로 규범을 고쳤다.** 필살기 양방향 가드
("검수 발견을 그대로 신뢰하지 말고 종합 단계에서 거른다")를 정확히 위반했다.

**반증은 엄밀했다** — 세 유형으로 갈렸다:
1. **형식 계약을 결함으로 오인**(최다). 검수자가 "변형 단락이 연결사를 바꿔 게이트 #10 을 우회했다"고
   지적했으나, `gate-order-variant.ts:295-308` 은 **단서를 지우면 반려**하고
   `ORDER_CUE_KINDS(:74,77)` 가 그 대체 표현(`despite`, `one example`)을 **승인 어휘로 열거**한다.
   즉 우회가 아니라 **유일한 합법 해**였다.
2. **정량 주장이 재계산에서 붕괴.** "오답 4개 중 3개 즉사" → 실제 재계산 ITEM별 2/4·2/4·1/4·1/4.
   결정타: 정답 단락도 같은 블록리스트어로 시작해서 **"첫 단어 휴리스틱"이 아무것도 소거하지 못했다.**
3. **구판본 검수**(2건). 타임스탬프로 증명됐다 — `review.json 17:11:53 → md 17:22:49 → gate.json 17:24:08`.
   검수 11분 뒤에 저작 풀이 파일을 다시 썼다. **이건 검수자 잘못이 아니라 내 공정 결함이다** —
   저작 풀(prod-2027-001, q20/q22)이 도는 중에 같은 유닛에 검수를 걸었다.

**확정 기준 재산정**: 보고된 `C8·D5·F5` 는 미검증 지적 기반이다. 확정 critical 로 다시 매기면
**F 0개 · D 6개 · 나머지 12유닛은 확정 critical 0.** 그림이 완전히 다르다.

**조치**:
- 지침에서 **P1-b 전면 삭제**. 자기반증 11번은 "즉사 2개 초과면 설계를 다시 보라"는 약한 형태로
  강등하고 *"재작성 트리거가 아니다 — 반증 단계가 2/4 를 정상으로 판정했다"* 를 명시.
  잘못된 근거로 만든 규칙을 남기면 저자가 **모든 오답을 억지로 강화해 정답을 흐린다.**
- 검수 프롬프트에 **기각 사유 4종을 명시**해 다음 라운드가 같은 실수를 반복하지 않게 했다
  (형식 계약 오인 / 정량 주장 미검산 / 구판본 / 심각도 부풀리기).
- 교차검수 워크플로에 **저작 풀 종료 확인** 경고를 넣었다.

**교훈**: **적대적 검수의 산출은 결론이 아니라 가설이다.** 반증을 통과하기 전 숫자로
규범을 고치면, 잘못된 규범이 팬아웃으로 증폭된다. 그리고 등급을 raw finding 으로 매기면
**멀쩡한 산출물을 F 로 오진**한다 — 이번에 F 5개가 실제로는 0개였다.
